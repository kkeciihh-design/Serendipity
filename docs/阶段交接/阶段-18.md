## 数据与计价约定

仍为10个既有数据库迁移，无新依赖、无新表。保存于现有`PlanVersion.events/costs` JSON；历史记录没有新字段时兼容读取，不批量重写。

- `PlanCostItem.dinerCount?: number`：1–100整数，仅餐饮`category=meal`且`unit=per_person`使用。本餐行代表1餐，合计=人均整数分×dinerCount；无字段时按原规则使用计划自身`requestSnapshot.travelerCount`。`quantity`仍仅用于按票，未改变其他项目计费。
- 原一次性餐费是总价，不自动解释成人均；卡片展示原合计、把人均输入留空，并在预览中明确新计价。下限未知时上限也必须未知；null与0区分。
- 餐厅面板的手填金额是预算估算（`certainty=estimated`、`source=ai_draft`），不会标已付或已核验。真实支付/确认仍在预算入口处理；该入口保留dinerCount，改成一次性总价时清除乘数。
- `PlanEvent.restaurantSelection? = { catalogId: string|null, action: 'adjust'|'replace', selectedAt: ISO_UTC, invalidatedAccessOrigins?: [{ticketId,originName}] }`。仅记用户选择/接驳失效，不授权预约、支付或锁定；AI DTO会剔除此字段。
- `invalidatedAccessOrigins`记录被替换餐厅曾作为有效票据人工接驳起点的关系。派生红线不能继续使用旧店耗时；提示门到门入口更新起点/接驳。票据原事实不改。重新选择回原地点或票据起点改变后，旧标记不再作用；普通本餐估算编辑保留仍相关标记。
- 所有新版本继续继承原snapshot/R；最新需求已修改时仍标待更新。**修改本餐人数不会改整趟人数、预算目标、其他餐次或同行车票。** 不绕开既有需求更新协议。

## 接口与原子替换

基础路径`/api/trips/:id/plans/:version/restaurants`：

- `GET ?eventId=...` → `{recommendations}`，包含当前卡、最多3候选、排除原因、原合计及编辑权限。无目录/无法匹配具体分店时返回空资料与说明，仍可记录本餐估算。
- `POST {action:'preview', eventId, candidateId:string|null, pricing:{dinerCount,minCents,maxCents}}` → `{preview}`。null保留当前用餐并调整估算；其他门店先建立拟议快照，检查再预览。预览不写库。
- `POST {action:'apply', eventId, previewToken}` → `{plan}`。服务器token绑定旅行、旧版本、事件与全部候选/金额；apply不接受客户端改写预览费用/地点。

缓存最多100项、10分钟，重启自然失效；路线有数据时应用前检查15分钟新鲜度。价格调整应用前重读当前餐厅营业/位置冲突。事务再次核对当前版本、稳定事件类型/ID、锁定/确认、有效票据及受保护费用；一次保存事件、地点、费用、路线、待办与来源，再更新唯一当前版本。并发仅一项成功，数据库失败全部回滚；历史只读。

替换保持稳定eventId，用建议用餐时长更新结束时刻。已有相邻路线逐段复查：断网、人工公交原参考或精确POI缺失时清除旧路径/耗时，保留未知车费，不使整段旅行看起来免费；已有付款仍保留。没有既有路线时不编新线路，提示到地图补查。城市路线仍受既有同日/精确点与提供方能力限制。

字段来源按事件与餐费签名继承；dinerCount/价格或地点变化会使相关旧来源需复核。旧店停业/价格摘录仅保留审计，不能覆盖新店。营业和搬迁来源必须覆盖完整用餐窗口；参考营业资料与确定关闭分开。明确预算/步行上限、行程重叠、路线迟到及新增有效红线冲突会阻止应用。

客户端GET30秒、预览60秒、保存30秒超时；关闭请求中的预览中止并忽略迟到结果。保存超时提示刷新核对，不能声称数据库必未写。图片只允许受控本地路径、匹配具体实体/城市/许可，失败占位。
