## 1. 产品概述

### 1.1 产品定义

从一句自然语言开始，帮助一个人把一趟旅行安排明白，并在旅行中知道接下来做什么、怎么过去、何时必须行动。

产品最终交付的是能够执行、能够调整、能够随身查看的旅行计划。它包括时间、地点、交通衔接、预算、准备事项，以及每条重要信息的可靠程度。

核心分工：**程序负责计算，AI 负责理解和建议，外部数据负责核验，用户确认自己的实际安排。**

### 1.2 第一版工作假设

| 项目 | 默认决定 |
|---|---|
| 使用方式 | 个人、单用户、网页版；一个使用者可以为多人同行规划 |
| 旅行范围 | 中国大陆城市短途旅行，2～4 天；一个主要目的地城市及合理近郊 |
| 语言、货币、时间 | 简体中文、人民币、Asia/Shanghai；日期和时区仍完整保存 |
| 交通重点 | 高铁/飞机加城市公共交通；步行、地铁、公交、打车，必要时支持简单自驾 |
| 数据 | SQLite 和文件保存在选定运行实例的磁盘；默认在本机，选远程部署则在该实例；不以浏览器缓存作为唯一存储 |
| AI | 一个主模型加按需调用的工具；优先支持经实测的 OpenAI Compatible 服务 |
| 运行 | 默认在这台电脑运行；旅行途中离线查阅用导出件，在线使用可采用同一应用的个人 HTTPS 单实例部署 |
| 范围原则 | 本文件列出的全部必需功能组成完整第一版；中途可用版本只是开发里程碑 |

不支持的旅行类型应明确提示，例如跨国签证规划、复杂跨时区、多城市长途串联。不能默默截断用户需求，用户可以修改为当前支持的范围。

### 1.3 需求审查与处理决定

| 原需求中的问题或缺口 | 本文采用的处理方式 |
|---|---|
| 时间示例出现两次到站，而且安检完成早于其中一次到站 | 使用唯一、连续的时间链。第 15 章给出重新核算后的 08:55 算例 |
| “时间红线”混合了发车时刻、办理截止和安全建议 | 分别显示固定时刻、经核验的业务截止、程序计算的建议最晚行动时间 |
| “还有 8 分钟”同时要求“必须现在出门” | 08:47 显示“建议 08:55 前出门，还有 8 分钟”；到时再提示行动 |
| 预算没有区分全程/每人、已消费/将要发生 | 明确人数、计价单位、晚数与费用状态；示例分项合计确为 1,286 元，以后同样由程序汇总 |
| 本地网页与离家后的手机在线使用没有连接方案 | 明确本地、离线导出、个人 HTTPS 部署三种可达性；响应式布局本身不算远程可用 |
| 管理员设置排到最后，前面却需要真实 AI | 阶段 4 提供最小设置；地图、搜索、天气配置随功能加入同一个页面 |
| “单用户”可能被理解为只能一人旅行 | 无多账号，但保留同行人数、每人/全程预算、按房间计算住宿 |
| 车票识别后直接成为硬约束可能放大识别错误 | 自动识别并填入草稿；用户确认关键字段后自动入行程、重算红线 |
| “周末”“1500 左右”“从深圳出发”不够精确 | 展示具体日期和预算口径；必要时只追问会影响执行的缺口。出发点允许附近地铁站或地标 |
| 实时余票、房态、排队、营业状态未必有合法可用接口 | 按实际可获得能力核验；未知就标未知，提供官方入口，不能靠模型补造事实 |
| 图片要求未定义来源和不可用处理 | 正常展示 1～2 张有出处的相关图片；缺图时诚实占位，不拿其他门店或生成图冒充 |
| 地图连线可能被误认为真实道路 | 道路路线与跨城示意连线分开表达；真实路径由地图服务提供 |
| 重规划可能破坏已订车票、已消费费用 | 冻结已发生事实和已确认硬约束，生成新版本并统一重算派生结果 |
| “已核验”粒度不明 | 核验到字段；位置有来源不代表价格、营业、预约也有来源 |
| 日常启动、备份、断网、服务失败未定义 | 加入可点击启动、稳定数据目录、中文错误、备份恢复及降级验收 |
| 自动测试能否替代所有真实事实检查 | AI 负责软件验收；模拟接口不能证明真实服务可用，软件通过也不代表未来交通一定准点 |

### 1.4 三种使用状态必须说明白

| 状态 | 能做什么 | 条件与边界 |
|---|---|---|
| 电脑本地完整应用 | 规划、改行程、地图、保存、导出、执行模式 | 电脑和服务运行；AI、地图等联网功能需要外网及有效配置 |
| 手机离线资料 | 打开已导出的手机一页版、长图、PDF、文字 | 出发前保存；不提供实时地图、天气或 AI 重规划，显示导出时刻 |
| 手机在线完整应用 | 在旅行途中访问同样的规划和执行功能 | 需要可访问的个人 HTTPS 单实例及持久化磁盘；全站用一个个人密码保护，无多用户系统 |

同一可信局域网可用于手机体验，但电脑关闭、离开网络就不可用。默认不开放公网、不依赖临时免费隧道长期运行。若作者选择旅行途中在线重规划，阶段 29 必须交付并验证个人 HTTPS 运行方式；没有实际部署时，交付说明只能承诺本地完整应用和离线资料。

一次选择一个主要运行实例作为旅行数据的保存位置。改为个人 HTTPS 实例时，AI 使用备份/恢复搬迁旅行，手机和电脑访问该实例；本机副本与远程副本不会自动同步，不能同时编辑后假定两边一致。

## 2. 产品目标

1. 一句话开始，必要时少量追问，得到 2～4 天的旅行安排。
2. 从出发地点衔接到车站/机场、目的地、酒店、活动、返程及回到出发地点。
3. 让用户随时看到下一步、下一条时间红线，以及相关信息是否需要确认。
4. 路线、时间轴、费用、清单和导出保持一致。
5. 对下雨、迟到和取消景点作出可解释的剩余行程调整。
6. 让零基础作者能够通过网页配置服务，通过 AI 完成后续维护。

第一版衡量方式：完成真实服务演练和第 21 章测试集；核心时间和预算计算对固定用例必须准确；第一版必需功能不能只停留在按钮或静态示例。推荐是否合口味允许后续迭代，不把主观体验伪装成百分之百命中率。

## 3. 用户画像

主要用户是希望少做攻略、喜欢轻松旅行的个人使用者。可能独自出行，也可能替朋友或家人规划；更关心“这条路线适不适合我”“今天会不会太赶”“赶不赶得上车”，不希望填写长表单。

项目作者没有开发经验。应用中的错误应解释为“模型连接失败，请到设置检查服务信息”，不能只显示堆栈、错误码或要求打开控制台。

用户仍会作出的正常产品决策：目的地、具体日期、预算口径、个人偏好、购买/预约决定、票面确认，以及对新方案的取舍。这些不属于技术验收。

## 4. 核心使用流程

### 4.1 第一次使用

AI 安装并启动项目 → 自动打开首页 → 用户设置个人密码 → 在设置中填写服务信息 → AI 检查真实连接 → 用户输入旅行想法。

未配置 AI 时允许使用明显标注的示例，不能将示例包装成已连接的真实生成结果。

### 4.2 计划一趟旅行

一句话输入 → 提取需求 → 展示具体日期、人数、预算和偏好 → 补问必要信息 → 用户确认 → 生成基础计划 → 程序检查时间/预算 → 逐步补充真实地点、路线和来源 → 展示行程总览、每日时间轴与地图 → 保存。

存在未订票、未确认地址或未核验预约等问题时，可以保存，但醒目列出待确认项。软件不能因为生成成功就宣布“全部可执行”。

### 4.3 加入自己的车票

上传截图 → 识别草稿 → 确认日期、车站和时刻 → 自动关联去程/返程 → 更新硬约束 → 重算出门时间与后续衔接 → 如有冲突，明确标出。

### 4.4 出发与调整

完成出发前清单 → 导出手机资料 → 开始旅行 → 查看当前步骤和下一条红线 → 手动标记到达/完成 → 输入“下雨了”或“晚了一小时” → 查看变更摘要 → 应用新版本。

如果现在已经赶不上既定交通，系统应输出冲突和可选择的处理方向，不能悄悄改掉车票或假装完成改签。

### 4.5 保存与再次打开

所有已提交编辑、清单状态和执行进度自动保存，展示“已保存/保存失败”；长耗时生成失败保留原版本。历史列表可以打开、改名、编辑、继续规划和删除旅行。

## 6. MVP 范围

本项目的 MVP 是一套完整但受约束的个人工具。全部 F01—F28 都属于第一版。允许通过多阶段到达完整第一版，不能把阶段 6 的文字行程就称为最终 MVP。

第一版采用以下简化方式控制成本：

- 只支持国内 2～4 天、主要目的地单城的常规短途；多人旅行不涉及多个账号。
- 每次推荐少量有解释的候选，一般 2～3 个；不做无限信息流。
- 交通提供可执行衔接与官方查询入口；无实时票务能力时明确待购票/待确认。
- 高铁截图识别属于第一版；机票可通过简短确认面板录入，机票截图识别后续扩展。
- 住宿先推荐区域，可给少量真实可查的酒店候选；不承诺实时空房和可订价格。
- 重规划先给一个可用新方案和变更摘要；保留上一版用于撤销，不做复杂历史系统。
- 移动端执行模式首先依靠当前时间和用户手动进度；定位是增强项，拒绝定位仍可使用。
- 首先实现一个真实 AI 适配器、一个地图服务及一个可用搜索来源，不同时集成多家同类服务。
- 四种导出共享同一份计划快照与渲染基础，分别独立开发和验收。

## 7. 暂不实现功能

不实现真实支付、自动购票、自动订房、自动预约、改签执行、多账号、团队协作、社交、会员、广告、企业权限、多管理员和复杂后台。

不引入微服务、Kubernetes、Redis、消息队列、多数据库、CQRS、事件溯源、向量数据库或复杂 Agent 集群。没有必要时也不引入容器。

暂不承诺后台精准提醒、锁屏持续定位、原生手机应用、全球跨时区旅行、专业道路导航、完整自驾车务管理、实时余票/房态/排队或跨设备自动同步。

“不承诺实时数据”不等于取消对应规划功能；用可追溯来源、估算标记和待确认流程完成当前范围。

## 8. 页面结构

| 页面 | 用户主要任务 | 主要内容 |
|---|---|---|
| 首页 | 开始一次规划，继续上次旅行 | 自然语言输入、少量示例、最近旅行 |
| 需求确认页/区块 | 确认 AI 是否理解正确 | 可编辑的简短摘要、必要追问、具体日期 |
| 旅行详情页 | 看懂并修改完整行程 | 总览、按天切换、左时间轴右地图、详情抽屉 |
| 推荐详情抽屉 | 决定是否保留某个地点 | 图片、理由、费用、预约、来源与前后路线 |
| 预算页签 | 判断花费是否合适 | 分类、金额区间、人数口径、超支提示 |
| 准备清单页签 | 确认票、预约、酒店、物品 | 分组勾选、临期提醒、办理入口 |
| 我的旅行 | 管理已保存旅行 | 搜索/列表、打开、改名、删除、继续规划 |
| 执行模式 | 在路上知道下一步 | 当前步骤、预计/真实位置、倒计时、下一条红线 |
| 导出面板与预览 | 选择随身查看方式 | 手机一页、文字、长图、PDF，导出内容选择 |
| 个人设置 | 无代码更换服务与偏好 | 密码保护、连接检测、Prompt 高级选项、备份恢复 |
| 手机底部“更多” | 找到较低频操作 | 设置、导出、历史旅行、退出执行模式 |

推荐的内部页面路径由 AI 在对应阶段建立：首页 /，历史 /trips，详情 /trips/旅行标识，执行 /trips/旅行标识/live，设置 /settings。不要提前建立空页面、无效按钮或大量路由。

状态必须覆盖：首次空白、正在保存、生成中、取消、成功、未配置、断网、限流、无数据、数据过期、路线不可行。保留用户已输入内容并给出下一步。

## 9. UI/UX 设计原则

### 9.1 视觉方向

现代旅行杂志的图片与留白，配合个人效率工具的信息密度。暖白底、深灰文字、低饱和自然色作点缀；红/橙/绿只承担明确状态含义。

避免满屏科技蓝、发光效果、重渐变、过多彩色按钮、过度圆角和层层套卡片。首页可以有一张有授权的旅行氛围图，行程页面优先保证可读。

### 9.2 信息层级

第一层：今天、下一步、下一条红线。第二层：每天的活动、交通衔接、预算。第三层：详细介绍、来源、计算展开项。

“为什么适合你”应在推荐卡片直接出现，例如“你偏好轻松漫步，这里与下一站步行约 15 分钟，能减少折返”。时长没有地图依据时必须标为估算。

### 9.3 桌面与手机分别组织

桌面详情采用左侧时间轴、右侧地图，建议约 45%/55%，结合屏宽调整。日期切换控制两侧同一天，详情以抽屉展示。

手机使用“行程 / 地图 / 清单 / 预算 / 更多”底部导航；执行模式把当前步骤和红线置顶。地图独立占据可操作空间，避免时间轴与地图挤在同一窄列。

### 9.4 可访问性与交互底线

- 正文手机优先 16px 左右，关键按钮触控区域至少 44×44 CSS 像素；红线不可藏在悬停提示里。
- 颜色必须同时配文字/图标；键盘可操作主要流程，焦点清楚，弹窗可关闭并返回原焦点。
- 文字与背景达到合理对比度，常规文字按 WCAG AA 的 4.5:1 目标检查；地图另提供同等信息的地点列表。
- 动画克制，尊重减少动画设置；加载占位不造成布局大幅跳动。
- 外部调用显示实际步骤，例如“正在核对地点”“正在计算路线”；不显示假进度百分比。
- 删除旅行要有确认，正在生成可以取消；关键输入失败后不丢失。
- 各阶段都检查 390px、768px、1440px 代表宽度；最后再整体打磨，不能等末期才支持手机。

| Tailwind CSS | 一致的颜色、间距和响应式样式 | 便于逐阶段修改；设计令牌集中管理 |
| 少量 shadcn/ui 组件与 Lucide 图标 | 按钮、弹窗、表单、抽屉 | 按需引入，保持普通用户熟悉的操作方式 |
| SQLite + Prisma | 旅行记录、版本、设置、清单 | 单文件数据库；迁移和读写便于 AI 管理，不需要数据库服务器 |
| Zod | 检查 AI 返回值和用户输入 | 让不合格式的数据在保存前被拦住 |
| date-fns 与一致的时区处理工具 | 日期显示、日期和时长计算 | 不手写容易出错的字符串时间运算；具体组合在阶段 0 验证 |
| Vitest | 时间、预算、约束等逻辑测试 | 快速运行确定性测试 |
| Playwright | 浏览器流程、截图，后期共用 Chromium 导出 | 验证真实交互，减少两套浏览器渲染实现 |

阶段 0 由 AI 查询并选择当时互相兼容的稳定版本，锁定依赖并记录。本文不凭记忆指定“最新版本”，也不允许开发途中无理由升级框架。

所有涉及数据库、密钥、AI 请求和导出的逻辑运行在服务端 Node.js 环境。SQLite 和浏览器导出不按 Edge 或只读、随时销毁的无状态运行环境设计。

### 10.2 单个应用内的边界

| 层 | 职责 | 禁止承担的职责 |
|---|---|---|
| 页面与交互 | 输入、预览、选择、状态反馈 | 保存服务端密钥，独立再算另一份预算 |
| 业务函数 | 时间红线、约束检查、费用汇总、版本更新 | 把未知营业时间猜成事实 |
| 外部服务适配器 | AI、地图、搜索、天气、图片的请求与统一返回 | 在业务页面散落厂商特定逻辑 |
| 本地数据 | 持久记录、事务、备份 | 把大批外部请求放在长时间数据库事务里 |
| 导出视图 | 从固定计划版本生成四种资料 | 重新问 AI 生成另一份导出行程 |

这里的“适配器”只是项目内少量普通函数和类型，不是插件市场、服务注册中心或复杂依赖注入框架。真正接第二家服务时再扩充。

### 10.3 开发与运行约定

AI 维护一个应用目录和一个稳定的数据目录。建议本机数据放在 Windows 的用户本地应用数据目录 Serendipity 下，页面展示实际路径和备份入口。本机可提供复制路径或由 AI 打开位置；手机/远程页面只说明数据存放位置并提供下载备份，不为打开文件夹引入桌面框架。

数据库、票据临时文件、导出缓存、脱敏诊断日志不放在网页公开目录，也不混进源代码或版本库。实际数据目录在首次安装时自动建立；作者不需要编辑环境变量。

开发测试使用独立测试数据库和人工测试票图，不能清空作者的旅行数据。升级前备份，由 AI 执行迁移；失败恢复原可运行版本。

第一版使用本机或有持久磁盘的单实例 Node 服务。临时请求状态可以存在内存，结果要落盘；不引入任务队列。若应用在生成中重启，任务标为中断并允许重试，不能让页面永久转圈。

### 10.4 运行性能目标

在已记录的开发机和受控网络上，已有旅行进入可读状态目标不超过 2 秒；外部地图随后加载。启动一次生成后立即给出加载反馈，目标 1 秒内，不等待完整 AI 输出才响应。

默认每次 AI 调用 60 秒上限、最多 1 次自动重试；完整规划通常不超过 120 秒。OCR、搜索和地图采用更短的独立超时。具体限值由实测调整并记录，不能靠无限重试掩盖失败。

使用地图懒加载、图片限尺寸/懒加载、普通列表和有限候选。只有实测出现问题才引入进一步优化。导出 Chromium 按需启动并关闭，同一实例同一时间处理一个导出，避免挤占本机内存。

## 11. 数据结构

### 11.1 保存原则

同一旅行只有一个当前生效计划版本。时间轴、地图、推荐卡、预算、清单和导出共同读取它；不各自维护一份独立“最终答案”。

先保存当前阶段真正需要的数据。以下是目标数据字典，不要求阶段 0 就建全表。

### 11.2 核心数据字典

| 数据 | 最少字段与含义 | 开始引入 |
|---|---|---|
| 旅行 Trip | 稳定标识、标题、原始需求、状态、创建/修改时间、当前版本号 | 阶段 3 |
| 需求 TripRequest | 需求修订号 requestRevision、当前修订确认状态、原话、出发城市/地点、目的地、日期、天数、人数、预算口径与目标、节奏、兴趣、住宿要求、限制、待确认字段 | 阶段 5 |
| 计划版本 PlanVersion | 所属旅行、版本号、结构版本、生成依据的 requestRevision 与 requestSnapshot（已确认需求快照）、完整计划快照、生成时间、简短修改理由、校验结果 | 阶段 6 |
| 地点 Place | 稳定标识、名称、城市、地址、经纬度、坐标系、地图服务地点 ID、地点类型 | 阶段 6 初步，11 补坐标 |
| 到访事件 Visit/Event | 稳定事件 ID、日期、地点 ID、顺序、开始/结束、时长、事件类型、是否锁定、状态、备注 | 阶段 6、8 |

为保持简单，Trip、PlanVersion、Settings 等少数对象使用独立数据库表；Place、Event、RouteLeg、CostItem、EvidenceFact 等可先存为经过校验的计划快照内容。Checklist 和 ExecutionState 根据写入频率再独立存储。只有查询或一致性需求明确时才拆表。

### 11.3 必须统一的规则

- 时间保存完整日期、时区和可计算时刻；纯“08:55”只用于显示，不能作为底层唯一值。
- 金额用人民币“分”的整数；距离用米、耗时用秒，界面再转为元/公里/分钟。
- 人均、全团、每房每晚、每张票、一次打车要有计价单位。多人住宿按确认的房间数和晚数计算。
- “同一个酒店”是一个地点；上午入住和晚上返回是两个到访事件。编号跟随事件，不跟随唯一地点。
- 地点 ID 与事件 ID 稳定；重排只改变顺序和展示编号。不要用数组位置当永久身份。
- 原话、AI 提议、用户确认、外部核验和程序推算分开保留，不能互相覆盖来源类型。
- “已确定费用”和“已支付费用”是两个维度。取消已消费项目不能自动退款或从实际花费中消失。
- 相同票据、路线、导出请求都有重复提交保护；多标签页修改使用版本号检查。

交通耗时与费用只算一次：相邻事件之间的城市移动由 RouteLeg 表达，时间轴的交通行从它派生；已经是独立固定交通事件的高铁/飞机不再重复作为同一段移动加入。酒店预订时段是住宿约束，不能当作整晚占满所有活动的事件。

### 11.4 旅行与计划状态

旅行可经历：草稿 → 需求待确认 → 规划中 → 计划待确认 → 已准备 → 旅行中 → 已结束。生成失败是可恢复的任务状态，不能把旧计划改成空记录。

单独保存可执行性：信息待补齐 / 可执行但仍有估算 / 存在硬冲突。只有日期、关键交通、必要路线和约束检查满足条件，才可以标为“可执行”。“已准备”也不代表预约已被平台实际完成。

### 11.5 版本与数据一致性

**需求修订与计划依据。** 阶段 5 引入 requestRevision，TripRequest 建立时从 1 开始。原话或影响规划的需求字段发生实际修改时，保存操作校验旧修订号，递增修订并清除当前修订的确认；沿用阶段 3 的修改原话入口也遵守此规则。用户只能确认自己看到的当前修订，过期确认被拒绝。需求提取请求记录起始修订，迟到结果不能覆盖已修改的输入；重复请求不得产生重复提交。

阶段 6 起，每个 PlanVersion 保存生成所用的 requestRevision 和不可变 requestSnapshot，包含当时已确认的需求、默认假设及必要来源。旧计划的展示、普通编辑校验、推荐、预算和导出始终使用它自己的需求快照。最新需求被修改或尚未确认时，旧计划明确标为“需求已修改，计划待更新”，仍可查看或导出旧依据；不得混入新目的地、日期、人数或预算，也不得把旧计划补标成使用了最新修订。

**生成与提交。** 新生成或重规划先读取当前已确认需求修订 R、当前计划版本 V，以及当时已引入的清单和执行状态版本，在事务外完成外部请求与计算。保存时短事务核对 R 仍是当前确认修订、V 仍是当前计划版本及所读状态版本仍有效，再提交完整 V+1 及其需求快照。没有计划时核对“当前仍无计划”后创建首版。期间需求变化，旧结果必须拒绝或重新计算，不能临提交才给旧输出补上最新 R、V。

用户修改需求不会解除当前有效票据、固定预约、锁定或已发生事实。新方案必须保留这些约束，冲突就说明原因，不靠删票制造可行。下雨、迟到等未改变需求字段的重规划可复用已有确认，无需重复填写；确实改变需求字段时先走相同的修订和确认流程。

普通编辑旧计划、确认真实票据或记录已发生费用可以继承该计划自己的 requestSnapshot/R，并产生计划新版本；它仍可能是待更新计划。新需求尚未确认不能阻止保存真实票据或已发生费用，也不能成为给旧计划改标最新需求的理由。票据确认、退票或替换与旧派生结果失效应一次提交；外部路线重查在事务外完成，按所读版本统一保存结果。资料不足或发生冲突时保留真实票面和待重算/冲突状态，不继续显示失效路线、红线或过时的“可执行”结论。仅 active 票据参与当前交通硬约束。

清单按稳定事项 ID 合并，保留仍相关事项的勾选；新预约默认未完成。旧导出保留但标为“来自旧版本”。撤销是创建一个新的当前版本，并按现在的时间和硬约束重新检查，不回退已发生事实。

清单和执行状态即使独立存储，也有修改版本。重规划提交时重新读取它们并检查版本，将刚完成的活动和勾选合并后再校验；不能使用请求开始时的旧状态覆盖用户最新进度。

候选预览前的校验不能代替真正应用时的校验。阶段 22 在用户应用时读取最新时钟并复核剩余行程；所需路线重查在事务外完成。提交短事务同时检查版本、需求确认及本次校验的行动边界/路线有效窗口仍成立，事务内不调用外部服务。已不可行则拒绝应用；重算导致活动、计划时刻、路线或费用实质变化时先更新预览，再由用户应用。倒计时正常流逝不算方案内容变更。撤销继续遵守当前时间和事实保护规则。

导出也要一次取得相互一致的计划、该计划的 requestSnapshot、清单和执行状态快照，并记录各自版本；不能在生成多页期间不断读取变化中的数据。页面秒级倒计时无需每秒写入数据库。

**恢复后的旧写入失效。** dataGeneration 和持久恢复屏障只在阶段 28 引入，之前不预建恢复模块。dataGeneration 是运行实例的简单代际标识，正常重启保持不变，不属于旅行备份，也不得随历史数据恢复回退；它补充业务版本检查，不替代登录保护。阶段 28 同时把代际检查接入既有需求、旅行、票据、计划、清单、执行状态、候选应用及异步产物登记入口。

恢复文件先校验并预览影响，用户确认后设置持久恢复屏障，暂停新业务写入和新规划任务；只读状态展示可以保留。所有提交事务都要重新检查屏障与请求起始 dataGeneration，防止恢复前已在途的写入绕过入口检查。屏障内先制作并核对一致性安全副本，再替换旅行数据。成功时在同一短事务中提交恢复数据、换成新的 dataGeneration 并解除屏障；保留管理员和服务配置。

恢复失败并保护或回退数据后，也先换代再解除屏障。进程中断时保留恢复状态，下一次启动先安全完成恢复或回退、换代，再开放写入，不能直接清除屏障。阶段 28 之后的技术恢复/回退同样遵守换代规则。外部请求、文件校验和备份制作不放入长数据库事务。

旧页面、旧候选和迟到响应必须以原代际提交并被拒绝；不得仅补上最新代际重试旧载荷，必须重新读取当前业务状态。即使恢复后计划版本再次出现同一个数字，旧结果也不能落盘成为当前有效结果。已下载的历史文件不扫描删除，仍保留其版本说明。

## 12. AI 架构

### 12.1 主流程

自然语言 → 需求提取 → 必要追问 → 用户确认 → 候选安排 → 外部资料获取 → 程序约束检查 → 完整计划快照 → 展示。

这是一个主 AI 在几个受控步骤中调用工具。步骤可以先后使用同一模型；不建立景点 Agent、餐厅 Agent、交通 Agent 等多 Agent 业务系统。

### 12.2 AI 应输出什么

AI 输出结构化需求、候选地点、建议活动时长、偏好匹配理由、待核验字段、约束冲突解释与备选安排。

AI 不直接决定最终预算合计、红线时间、坐标正确性、是否有余票、是否预约成功、是否存在房间。AI 返回的日期、时长和地点也必须通过输入校验及业务检查。

对“周末”“后天”等相对日期，以实际运行时钟和用户时区解释并展示具体年月日，不把本文编制日期硬编码进程序。天数包含出发日和返程日，住宿夜数通常为天数减一，但夜车、凌晨抵达等需另行确认。

### 12.3 追问策略

每轮只问 1～3 个影响当前步骤的关键问题。通常先确认目的地、出发城市、具体日期；“1500 元”默认可建议为全程总预算，但必须显式显示供确认。

节奏、兴趣、住宿档次等可给可修改默认值。计算门到门红线前才要求确认精确出发点、车站/机场及票面时刻。没有家庭详细地址时允许以附近地点为起点，并提示家到该地点的一段仍待补。

对目的地不存在、日期已经过去、预算明显不足、5 天以上等情况，说明具体问题和可修改方向，不生成一份违背输入的“成功结果”。

### 12.4 Provider 与能力检测

最小适配器提供三个业务入口：理解需求、生成计划、识别票图。设置中记录文本、图片输入、结构化输出等实测能力；图片识别可以使用同服务的另一个支持图片的模型。

优先实现经过验证的 OpenAI Compatible Chat Completions 适配路径，以服务端配置 Base URL、Key 和模型。不得仅凭服务名称宣称兼容。若未来新增另一种接口协议，新增一个薄适配器即可，不重写页面和计算规则。

结构化输出可用时采用服务支持的 Schema；不可用时要求 JSON 并由 Zod 校验。两种路径都需要业务校验。拒绝、截断、空响应、格式错误不当成有效计划；格式修复最多一次，仍失败则保留旧数据并报告。

官方 OpenAI 文档说明了结构化输出的 Schema 能力及拒绝/截断等边界，也说明视觉模型可能读错小字、旋转图等。第三方“兼容”服务的功能仍需逐项实测，不能由官方文档代替其验收。

### 12.5 提示词与工具控制

提示词分为应用不可关闭的业务规则、可编辑的系统/基础 Prompt、当前用户需求、经过标注的外部资料。Prompt 可以改变表达风格和偏好，不得关闭程序时间校验、密钥保护、来源规则或硬约束检查。

外部网页和 OCR 内容一律作为资料，不作为指令。工具只提供当前阶段需要的查询，返回值先验证再使用；模型不能任意请求文件、执行命令或代用户购票。

控制上下文大小、地点候选数、外部查询次数和修复次数；最多一个规划任务作用于同一旅行。取消后阻止结果写入，不能承诺已经发出的外部请求一定不计费。

## 13. 外部 API 设计

API 对作者可以解释为“应用连接外部服务的通道”。开发时统一处理成功、无数据、不支持、未配置、鉴权失败、限流、超时和服务错误，页面显示对应中文信息。

### 13.1 首选方案与替换边界

| 服务 | 第一版选择与必要能力 | 替换边界与不可承诺 |
|---|---|---|
| AI | 一个经过实测的 OpenAI Compatible 服务；文本必需，票图需要视觉能力 | 业务层不依赖某一模型名称；不假设所有兼容服务支持图片和结构化输出 |
| 地图/路线 | 优先评估高德 JS API 与 Web 服务，覆盖国内地点、步行、公共交通、驾车 | 若账号权限/地域/授权无法满足，阶段 11 前说明并换成一个可用服务；不同时集成多家 |
| 搜索/来源获取 | 首先评估一个可在作者环境访问的搜索 API，例如 Tavily；结合官方网页读取 | 搜索摘要用于发现资料；中文覆盖、权限、费用和网页可读取性以实测为准 |
| 天气 | 优先复用选定地图提供方天气能力；范围不足时再评估单一替代服务 | 超出预报天数不编天气；不为预期未来需求先集成两家 |
| 地点图片 | 允许展示的地点资料/官方或授权来源；必要时使用明确标注的通用氛围图 | 展示权与导出权分开检查；不保证任意门店都有两张真实图片 |
| 铁路/航空 | 用户确认的票据及官方查询入口；有合法可用接口时才接 | 不假设存在免费、稳定的余票/报价接口；不抓绕登录、验证码或反爬 |

开发 AI 在相应阶段开始时记录：所选提供方、实际验证的能力、账号权限、可用地区、费用/额度、允许缓存与导出条件。本文未开通任何服务，也未验证作者的账号权限。

### 13.2 统一返回内容

每次外部调用保留请求标识、状态、数据、来源、获取时间、数据适用时间、到期策略、能力限制、用户可读错误。可选费用信息存在时记录，不存在时不猜精确调用价格。

地图路线另外记录：完整出行日期、路线实际针对哪个出发时刻或有效窗口、是否包含候车/步行/换乘、是否为实时路况、是否能查未来公交。无未来时刻能力时注明“按当前可得资料估算”，不能把在一个时刻查询的候车和乘车总耗时直接用于另一个时刻。

缓存仅用于省时和减少调用，在来源允许范围内按地点、方式、完整出行日期及适用出发时刻/有效窗口形成键；过期或跨出窗口后不得继续当作适用结果。窗口必须有来源依据，不能自行把全天当作同一班次条件。首次实现用本地数据库或内存短缓存即可。

阶段 13 验证按不同时刻查询/读取路线得到对应班次与耗时；阶段 15 再把这项能力用于红线倒推和从建议出发时刻的正向复核。候选时刻复核最多 3 轮（含首次正向复核）；到上限仍不一致或没有所需能力时保留估算/待确认，不无限请求，也不宣称精确可执行。

### 13.3 密钥、网络与可替换性

AI、搜索、天气和 Web 服务密钥只在服务端使用。地图浏览器 Key 可能按产品设计公开，应限制可用域名和额度；地图安全密钥留在服务端，通过受限代理使用。

外部网页获取限制协议、内容类型、大小、超时和跳转，防止访问本机敏感地址或把登录资料发往未知站点。用户明确配置的本地模型服务可以单独允许回环地址，不与任意网页抓取混用权限。

第三方内容作为不可信数据转义显示；不可直接把 AI HTML 或外部脚本渲染进页面。诊断只记录必要元信息，隐藏密钥、精确住址和无关票面个人信息。

来源链接保存可公开的资料地址或供应方记录标识；含 API Key、访问令牌或临时签名的请求 URL 不能直接写入来源展示、日志和导出。

以下资料在 2026年10月8日读取，用于确认设计边界；实施时仍需复核版本、账号权限与服务条款。

- [OpenAI：Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)——结构化输出、Schema 限制、拒绝与未完成响应处理。
- [OpenAI：Images and vision](https://developers.openai.com/api/docs/guides/images-vision)——图片输入及小字、旋转、识别错误等限制。

这些是技术设计依据，不是本示例旅行的车次、门票、营业或天气来源。

## 14. 地图设计

### 14.1 地图首先是行程阅读工具

选中一天后，显示当天出发点、交通枢纽、住宿、景点、餐厅和其他安排。地图地点来自已保存行程，时间轴和地图共用日期、选中事件和版本。

跨城当天提供交通概览和目的地城市详图；不能为了同时装下深圳与长沙而把当地所有景点缩成一团。PDF同样优先保证当地编号与路线可辨认。

地点搜索需要城市和名称，必要时补地址或让用户选候选。找不到具体地点时显示“待确认位置”，不能悄悄用城市中心代替。酒店区域还不是已订酒店，地图用区域或“区域参考点”表达。

国内地图统一采用提供方所需坐标系。保存原坐标系，转换集中在地图适配层完成；不要把浏览器定位的 WGS84 与 GCJ-02 直接混画。

### 14.2 编号以到访顺序为准

一天内的可定位事件按顺序编号 ①②③……；站内无法独立定位的小步骤可作为其父节点下的时间行，不强行画一个虚构地点。

返回同一酒店可以对应 ②和⑧两个事件。在重叠坐标处展示组合编号或可选择的到访列表，点击后选择对应时段。下一天重新编号，但稳定事件 ID 不变。

### 14.3 双向联动

点击时间轴事件：更新选中状态、让地图定位并展开对应地点摘要。点击地图编号：切换到正确日期/事件并滚动时间轴。手机点击地图点可先打开底部摘要，再“查看行程”跳转。

地图拖动不得自动修改顺序。用户切换日期、打开详情、重新规划后选中项应保持有效；被删除事件不残留悬空选中状态。

### 14.4 路线与方向

逐段请求相邻地点的路线，在真实返回折线上展示箭头和交通方式。地铁/公交显示上车站、线路、方向、换乘与下车站；步行显示时间/距离；打车显示驾车预计耗时、另列候车估算。

高铁、飞机无真实轨迹时可画带方向的跨城示意连线，明确“仅表示顺序，非导航路线”。不得把景点间直线连接标成步行路径。

行程图例可以用线型配合少量颜色区分交通方式。选择某段时突出该段并显示前后站，地图上始终保留来源署名及必需标识。

### 14.5 地图失败与导出

地图不可用时保留按顺序排列的地点、地址和已有路线文字，提供重试；估算线路与缺少数据明确标注。不能把地图加载失败等同于旅行数据丢失。

阶段 11 就验证地图是否允许用于长图/PDF，是否有可用静态图或合规渲染方式。导出需要每日静态地图和编号，不能等最后才发现无法合法导出。若首选服务不满足，应在尚未铺开依赖时更换可用方案。

可提供跳转地图应用的导航链接，带上已确认地点与方式；用户是否安装对应应用不影响时间轴使用。专业实时导航由地图应用承担。

## 15. 时间红线设计

### 15.1 三类时间分开表达

| 类型 | 例子 | 来自哪里 |
|---|---|---|
| 固定时刻 | 已确认 10:35 发车，预约 14:00 入场 | 用户确认的票据/预约，或适用的可靠来源 |
| 办理截止 | 停止检票、停止值机、停止托运、停止入场 | 对应站点/班次/日期的有效规定；未知时不能假定为已核验 |
| 建议最晚行动时间 | 建议 08:55 前出门、建议 09:50 到进站口 | 程序根据已知约束、路线、办理耗时和缓冲倒推 |

车站大小、首次到访、周末/节假日、人流、行李、步行能力、换乘会影响相应环节耗时或缓冲。每个加量显示原因，不产生一个无法解释的“AI 安全系数”。

节假日来自适用年份的可信安排或用户明确选择，不能只把周六周日当作所有节假日。产品默认耗时是可调整的估算值，不能写成铁路或航空统一规定。

用户在“红线详情”修改首次到访、行李、步行能力和额外缓冲，立即看到重新计算的结果；通用选择可保存为个人默认值，不要求修改代码常量或 Prompt。

### 15.2 确定性计算方法

建立普通的有序步骤表：起点步行、候车、乘车、换乘、进站安检、站内步行、必要办理、到检票/登机口。先区分固定耗时与随出发时刻、班次或路况变化的耗时。

对固定耗时，或已经选定并经适用时刻核验的连续链，对每个必须满足的截止点 j 计算：

**满足该截止点的建议最晚出发 = 截止时刻 j − 从起点到该截止点的必要耗时 − 对应的机动余量。**

存在多个截止点时取更严格的建议。公交、地铁等有班次的路段不能把另一个时刻查询出的总耗时当常量相减；按已取得、覆盖相关时段的班次/路线资料选取满足截止的可行衔接，再反推到起点。不要求建立复杂调度优化系统，也不承诺超出资料覆盖范围的全局最优时间。

必须从**计算出的建议出发时刻**正向复核整条链的班次、候车、换乘、运营时间及每个截止，并另从真实当前时刻检查是否仍来得及。所用路线跨出适用窗口时重新查询或重选候选，再复核新时刻；最多 3 轮候选时刻复核（含首次）。仍不一致、无未来时刻能力或关键资料缺失时显示估算/待确认及原因，不把未核验的建议标为精确可执行。候选在预览后应用还要按第 11.5 节重新检查当前时钟。

特殊约束“至少提前 X 分钟到达车站”要换算成该地点的到达截止，与原约束比较取更严格值。不能在已经计算安检和站内步行后，又机械追加整个“提前到站 X 分钟”。路线总项、分项及缓冲仍各计一次。

T28 使用固定演示输入：公交 09:00、10:00 发车，步行到站 10 分钟，乘车 30 分钟。08:45 查询得到候车 5 分钟、总耗时 45 分钟；最终截止 10:00，缓冲 10 分钟。直接倒推的 09:05 出门会在 09:15 到站、错过前班，实际 10:30 才到，不能通过。应返回能赶上适用班次且经正向核验的建议，或明确资料不足；不能仅凭 08:45 出发可行就认可 09:05。

### 15.3 经修正的 08:55 算例

**以下均为测试演示输入，不是深圳北站或某车次的真实规定，也不是实时地铁路线。** 假设 10:35 发车，本例另假设停止检票为 10:30。

| 环节 | 演示耗时 | 正向时间 |
|---|---:|---|
| 出门步行至地铁站 | 10 分钟 | 08:55—09:05 |
| 地铁候车 | 5 分钟 | 09:05—09:10 |
| 地铁乘车 | 30 分钟 | 09:10—09:40 |
| 地铁出站至铁路进站口 | 10 分钟 | 09:40—09:50 |
| 排队、进站、安检 | 20 分钟 | 09:50—10:10 |
| 站内步行至检票口 | 10 分钟 | 10:10—10:20 |
| 机动余量 | 10 分钟 | 10:20—10:30 |
| 假定停止检票至发车 | 5 分钟 | 10:30—10:35 |

倒推：10:35 − 5 − 10 − 10 − 20 − 10 − 30 − 5 − 10 分钟＝08:55。

面向用户显示：“今天第一条时间红线：建议最晚 08:55 出门。预计 09:50 到进站口，10:20 到检票口，预留 10 分钟机动余量。停止检票时间仍需按实际车次确认。”

此时 08:55 不能被标成“官方最晚出门时间”或“保证不误车”。

### 15.4 避免重复计算

- 地图如果已给出包括步行、候车和换乘的总耗时，不能再把分项重复相加；展示总项或展开明细二选一参与汇总。
- 安检预计耗时是流程本身，机动余量是额外不确定性。周末加量只能应用到明确环节或总缓冲的一处。
- 打车行车耗时与候车耗时分别记录；地图没有叫车数据时不能省略或冒充实时。
- 往返车票分别生成红线，返程起点使用那时的实际/计划位置，不能沿用去程的家地址。

### 15.5 颜色、倒计时与不可行

“时间红线”作为重要模块明显置顶；颜色表达现在的紧迫度，文字另说明是固定截止还是建议时间。

默认提示规则：距建议行动时间超过 15 分钟为绿色；大于 0 且不超过 15 分钟为橙色；到时或已过为红色。阈值是产品提示策略，不是交通规定。

基于上述算例，家到检票口必要耗时是 85 分钟：

- 08:47：显示“建议 08:55 前出门，还有 8 分钟”。
- 09:00 才出发：预计 10:25 到检票口，缓冲只剩 5 分钟；显示“已过建议出门时间，余量不足”，不武断说必然误车。
- 09:06 才出发：预计 10:31 到检票口，超过假定截止；标记当前路线不可行。
- 刚好踩在停止检票时刻不判为安全可行，不能把截止边界当作仍有余量。

不可行时寻找真实可得的替代路线；仍不满足就展示冲突和官方处理入口。不能擅自挪动列车时刻、假设列车晚点、删掉安检或缩短必需耗时。

如果截止本身尚未核验，结论必须写为“按当前假定截止和预计耗时无法衔接，截止仍待核实”；不能把条件计算升级成已证实误车。

### 15.6 跨日、航空和未知信息

00:35 发车、倒推 100 分钟，应显示前一天 22:55。还要检查那个时段是否有地铁/公交，不只做日期减法。

航空至少分别检查值机、托运（有行李时）、安检和登机截止；各截止来源不同，取最严格可行链条。没有托运就不套用托运耗时；国际航空流程不属于本版承诺。

缺少准确起点、站点、票面日期或必要路线时，可以给可见假设下的估算。确认字段后自动重算，旧红线立即标失效，不等待用户刷新。

页面倒计时按当前时刻重算，返回前台重新校准，不靠每秒减一累计。发现设备时钟与可获得的服务器时间显著不一致时提示时间不可靠；离线无可信校时源时如实说明使用设备时间。

## 16. 车票导入设计

### 16.1 第一版流程

上传一张高铁票截图 → 检查文件 → 识别 → 原图与字段并排预览 → 用户确认/修正 → 自动加入去程或返程 → 重算时间、路线、预算与红线。

这是避免手工重新输入的自动导入，关键字段确认仍是必要的用户操作。用户确认自己的票面不属于让用户承担软件测试。

### 16.2 字段与校验

必须支持识别：出发日期、发车时间、到达时间、出发站、到达站、车次、座位信息。截图本来没有到达时间或座位时标缺失，不补造；座位不是红线计算的前提。

额外保存到达日期和时区以支持跨日；缺年份或“次日”等要展示推断并确认。同城不同站必须映射到准确地点。

识别结果不可靠时标记具体字段，不只给一个整体“99% 成功”。模型自报置信度不当作可靠概率。即使看似清晰，日期、站点、车次和时刻仍须确认后生效。

多段票先列出识别出的各段，由用户选择导入；退票/改签界面不能不加判断地当作有效车票。第一版机票可以手动确认必要字段，保障飞机交通规划可用。

### 16.3 去重、纠错与冲突

图像文件指纹用于识别原图重复上传；交通类型、日期、车次、站点和可用座位信息用于提示疑似同票，不直接合并。同行者可乘同一车次不同座位，不要求为去重采集姓名或证件号；界面让用户选择“同一张票/同行者的新票/替换原票”，同步核对数量，防止重复交通或漏算人数费用。

票据使用稳定 ticketId 与简单状态：draft（识别或手工草稿）、active（用户确认有效）、cancelled（用户确认已退票）、replaced（已被指定新票替换）。保留票面确认时间和来源；票面曾经确认不代表现在仍有效。只有 active 票参与当前交通硬约束，缺失字段继续按原有规则标待补，不造事实。

阶段 14 的手动票面面板提供确认有效、记录已退票和替换指定票的入口；阶段 16 识别后复用它。退票/改签截图只提供待确认资料，不能自行把旧票停用或把截图中的票当新有效票。用户明确确认已办理的事实后才改变状态，应用不执行退票、改签或退款。

替换时明确原 ticketId，一次提交新票 active、指定原票 replaced 及 replacedByTicketId，并创建当前计划新版本；退票时只将指定票改为 cancelled。状态纠错同样需要用户明确确认并复用校验与提交入口。状态修改、旧约束解除及已引入派生结果失效一次完成，外部重查放事务外；按所读版本更新相关交通事件、地图地点、接驳路线、时间轴、费用，以及阶段 15 后的红线。失效结果不能继续作为当前可执行依据。

同行票可共享同一交通事件，但保留各自 ticketId、票数和对应费用。共享事件依据仍 active 的票保留或更新；替换一张不能静默改动其他票，最后一张有效票停用后解除该事件的票据硬约束。同行者分到不同班次、无法由本版单线行程统一表达时保存真实事实并提示冲突，不擅自合并或扩展多人分路规划。

退票或替换不等于退款到账：旧票面历史和已发生费用保留，退款金额及新费用须经用户确认，沿用阶段 9 的支付/费用规则计算，不自动归零。票图没有金额时不能将原估算改成零元或“已确定”。

确认前取消、识别失败、格式错误均不改变当前行程。用户已确认的新票、退票或替换产生冲突时仍保存真实事实并标明冲突；路线暂时查不到时保留待重算状态，不忽略真实票面，也不沿用旧红线装作可行。最新需求待确认不阻止这种事实保存，计划需求依据按第 11.5 节继承，不能偷偷换成最新需求。

票据编辑、退票记录、替换与截图导入走同一套校验、版本提交、失效和重算逻辑。T30 分别验证有效票确认退票、替换指定票、两张同行票只替换一张；阶段 14 仅验当时已有模块，阶段 16 追加红线及识别路径，避免提前实施未来能力。

### 16.4 文件与隐私

首版接受 PNG/JPEG/WebP 静态图片，单张默认不超过 10MB，服务器验证实际类型和像素量。HEIC/PDF 等暂不支持时给出清晰说明；不把文件名当安全路径。

默认仅临时保存原图，用于确认；确认成功后删除，未完成的上传在 24 小时后清理。结构化票面只保留旅行必需字段，姓名/证件号码不作为识别目标，座位不默认进入分享导出。

上传前说明图片会发给已配置的识别服务；提供裁剪/选择票面区域的方式，AI 技术测试使用人工脱敏样本。原图不得写入日志、网页公开目录、普通旅行备份或公开链接。

裁剪发生在发往识别服务之前，只发送用户选定区域；不是识别完之后才隐藏无关个人信息。

## 17. 推荐系统设计

### 17.1 先判断能不能去，再比较适不适合

先过滤不满足硬约束的候选：确定闭馆、必须预约但时间不满足、路线无法衔接、无法满足用户确认的预算上限、违反用户明确限制。营业或预约未知时允许作为待确认候选，但不能安排为唯一无替代的关键环节。

对可行候选，再按兴趣匹配、节奏、绕路程度、时间窗口、预算、天气、排队资料和下一站衔接排序。第一版用可解释规则和少量候选即可，不训练模型、不引入向量检索。

用户选“舒缓”时减少主要景点数量，留出用餐、休息和交通余量；“少走路”应结合已知步行距离比较并解释取舍，用户给出明确上限后再严格校验。未知步行数据不能被当作零。

“1500 元左右”“尽量少走路”默认是排序偏好；只有用户确认的预算上限、每日步行上限等才作为严格硬约束。不能由模型自行创造不可见的阈值，把所有候选过滤掉。

### 17.2 每个理由要关联本次行程

好的理由说明取舍，例如“这里以室内展览为主，符合今天避雨的要求；距午餐地点较近，参观后仍有足够时间去返程站”。

理由必须引用真实存在的用户偏好和可用路线数据，不能凭空假设用户爱好。没有路线依据时用估算标签，不能编精确步行分钟数。

### 17.3 三类卡片规格

| 卡片 | 必须展示 |
|---|---|
| 景点 | 名称、1～2 张预览图、简介、个性化理由、游玩时长、门票/区间、预约要求、建议时段、上一站距离和方式、当前日编号、信息来源 |
| 餐厅 | 名称、1～2 张预览图、菜品、人均/区间、营业资料、上一站距离、可获得时的排队风险、推荐理由、人数适配、与下一站关系、来源 |
| 住宿区域 | 区域位置、适合原因、预算区间、到主要活动距离、次日衔接、返程站距离、噪声/通勤等已知取舍；可附少量酒店候选 |

没有可靠排队数据时写“暂无可靠排队信息”，不生成“预计排 12 分钟”。地图营业时段不等于实时正在营业；酒店参考价不等于可订房价。

### 17.4 图片策略

每张图关联具体地点或明确标为区域氛围图，保存来源、署名和展示/导出权限。图片加载失败显示简洁占位和“暂无可用图片”，卡片其他信息仍完整。

正常验收样本必须确实展示相关的授权图片；不能用全部占位卡片宣称图片功能已完成。也不要求在客观无图的每个地点强行找满两张。

## 18. 数据可靠性设计

### 18.1 字段级状态

| 状态 | 使用条件 | 用户能看到什么 |
|---|---|---|
| 已核验 | 对应事实有实际读取的可信来源，内容适用于出行日期且未过期 | 来源、查询时间、适用时间 |
| 用户已确认 | 用户确认自己的票据、地址、预约或实际情况 | 确认来源与时间，不冒充官方查询结果 |
| 建议确认 | 缺数据、来源不适用/过期、来源冲突或只得到搜索摘要 | 待确认原因及可用官方入口 |
| AI 估算/规则估算 | 模型建议、默认值或没有外部依据的推算 | 假设、范围、可修改入口 |

“地图预计 35 分钟”“天气预报”即使来源已读取，仍保留“预计/预报”性质。可信的预测不等于确定会发生。

每张卡可以概括“3 项已核验、2 项待确认”，不能因为店名存在就给整卡所有内容盖已核验标签。

### 18.2 核验对象与时效策略

下列是产品初始缓存/复核策略，最终按来源许可和数据性质调整，不是对真实性的保证。

| 字段 | 优先依据 | 初始复核策略与失效处理 |
|---|---|---|
| 车次/日期/站点/票面时刻 | 用户确认票面或合法官方数据 | 改签/新票即失效；出发前提示复核运行状态 |
| 停止检票/值机/托运 | 对应车站/承运方当期有效规定 | 不把旧规则永久套用；出发前再次提示确认 |
| 路线和耗时 | 地图路线结果、适用出发时间 | 执行前尝试刷新；可先按 15 分钟缓存，失败显示查询时间 |
| 天气 | 对应地点与日期的天气服务 | 可按 1 小时缓存；超出预报范围显示暂无有效预报 |
| 营业/闭馆/预约 | 官方通知、场馆页面或可靠地点资料 | 规划时读取，出发前 24 小时内再提醒检查；日期不适用即待确认 |
| 门票/餐饮参考价/酒店参考价 | 官方报价或有日期的可信资料 | 保存适用条件与区间；价格不表示有票/有房 |
| 排队 | 有时间戳的实际可信数据 | 没有即时来源就未知，不能将历史热度换算成当前人数 |
| 图片 | 对应地点的许可来源 | 来源、署名和导出许可保留，撤销授权后不继续使用 |

来源冲突时优先比较权威性、适用日期和具体条件，不能简单取最新抓取的页面。仍无法解决就标冲突，并提供更稳妥候选。

### 18.3 关键事实对可执行性的影响

已核实关闭的景点不能留作正常安排；必须预约却尚未预约的活动标为待办，并准备可行替代。精确出发位置或固定交通缺失时，红线只能是带假设的估算。

计划可在部分信息未确认时保存和导出，但整体状态与具体未确认项必须一起显示。导出保留生成时间、版本和必要来源，不能把网页的黄色提示在 PDF 中删掉。

## 19. 管理员设置设计

### 19.1 一个个人设置页面

阶段 4 开始实现，不建立单独后台系统。第一次使用设置个人密码；以后进入敏感设置要验证。默认回环地址运行时保护管理操作；局域网/公网开放时使用同一密码保护整个应用，无需账号注册。

密码以成熟算法哈希保存，使用有有效期的 HttpOnly 会话，敏感修改做来源校验和请求防伪。远程访问仅使用 HTTPS，限制重复登录尝试；无需 RBAC、多角色或审计平台。

### 19.2 设置项

| 分组 | 项目 | 出现时间 |
|---|---|---|
| AI 基本连接 | Provider、Base URL、API Key、文本模型、连接测试 | 阶段 4 |
| AI 能力 | 结构化输出检测、图片模型或同模型能力、能力测试 | 阶段 5、16 |
| Prompt 高级选项 | 系统/基础 Prompt、恢复默认、版本和生效提示 | 阶段 4 先给基础编辑，随模型功能验证 |
| 搜索 | 所选来源、API Key、连接测试 | 阶段 10 |
| 地图 | 浏览器 Key、Web 服务 Key、安全密钥、连接测试 | 阶段 11 |
| 天气 | 复用地图或所需单一服务配置 | 阶段 21 |
| 个人偏好 | 常用出发地点可选、预算口径、默认节奏 | 相应需求阶段 |
| 数据 | 备份、恢复、数据位置、清理导出缓存 | 阶段 28 |

表单用普通语言说明去哪取得相应信息，并链接官方入口。隐藏已保存密钥，只显示“已配置”和必要末尾字符；读取设置接口不得返回密钥明文。

### 19.3 保存和检测

先填写临时配置，再点“测试连接”；检测通过后仍由明确保存动作替换当前设置。失败保留上一套可用配置。检测区分文本、结构化输出、图片、地图加载、路线和搜索，不用一次简单文本回复冒充全部通过。

密钥在服务端加密保存；本地自动生成加密材料并限制文件权限，不要求作者管理密码学文件。普通备份不含服务密钥和登录会话，换电脑后通过页面重新填写。

忘记个人密码时由拥有本机访问权限的 AI 执行受控本地重置，不设置公开免密重置接口。备份恢复不得覆盖当前管理员密码或降低全站保护。

### 19.4 Prompt 的安全边界

更改 Prompt 只影响之后的生成，不静默改写已保存旅行。恢复默认前保留当前编辑以便撤销。程序的时间、费用、来源、票据确认和硬约束检查不能被自定义 Prompt 关闭。

## 20. 导出设计

### 20.1 四种格式共享同一计划

导出开始时固定一个已保存的计划版本，日期、人数、预算口径和目标取该版本的 requestSnapshot，并记录其 requestRevision；不读取当前待更新需求来拼接旧计划。四种格式使用同一份数据选择和格式化逻辑，不调用 AI 再写一份旅游文章。需求已修改时明确这是旧需求依据的计划，不能把旧导出标成已采用最新需求。

共同保留：旅行日期、版本/生成时间、时间红线、待确认事项。私密家庭地址和座位默认隐去或泛化，用户可在导出面板明确选择是否带出；密钥、原始票图和证件信息永不进入导出。

隐去地址时，同时移除可反推出住址的精确地图标点、路线起点、导航链接参数和图片元数据，改为用户选定的公共地标；保留已有红线并说明起点已隐藏，不另造一份错误交通耗时。

### 20.2 手机一页版

“一页”表示一份精简的手机行动视图，不要求把四天内容挤进一屏。默认按所选日期显示，可跳到其他日期；保留时间、地点、交通、下一步、红线和关键提醒。

提供独立 HTML 文件与网页预览。HTML 内置必要样式和可合法嵌入的静态资料，核心内容不依赖外链脚本、登录或服务器；网络关闭时仍能读。离线版不承诺实时天气、在线地图或重新规划。

手机系统对本地 HTML 的打开方式不一致，因此同面板提供已开发的长图/PDF入口作为可靠的相册/文件查看方式。需要验证实际支持环境并写明打开方法；不能只测试桌面预览。

### 20.3 纯文字与 Markdown

同时支持复制和下载 UTF-8 文本，可切换简洁纯文字或 Markdown。保留按日时间、交通、地点、红线、预算摘要、清单与关键来源。

复制权限不可用时提供可全选的文字和下载，不让复制按钮无反馈。不能依赖特殊字体、HTML 或图片表达唯一的关键信息。

### 20.4 长图

使用受控的导出 HTML 和 Chromium 截图，宽度按手机阅读设计，输出 PNG 或 JPEG。使用已合法缓存或可导出的图片/地图，等待加载完成后再截图。

不无限增大单张图片。超过已验证的像素/文件大小上限时，先按天分图或在自然段落分段，展示“共 N 张”并完整导出；不截断尾部。单张 2 天短计划和分段 4 天计划都要验收。

### 20.5 完整 PDF

采用相同的导出数据和专门打印布局，通过服务端 Playwright Chromium 生成 PDF。第一版建议 A4 纵向，内置可分发的中文字体，页眉/页码简洁。

必须含封面、旅行总览、每日行程与时间轴、每日静态地图和编号、景点/餐厅/住宿、预算、Checklist、注意事项和必要来源。内容多时合理分页，不把卡片标题留在前一页、正文挤到后一页。

地图保留供应方必需署名；图片带必要来源。地图/字体等关键资源加载失败时明确失败并允许重试，不能把缺地图的完整 PDF 当成验收通过。若用户主动选择“简化资料”，需与完整 PDF 清楚区分。

### 20.6 导出验收与文件生命周期

AI 实际生成每种格式，读取文字内容、核对版本和关键数值，并渲染检查图像/PDF全部页面。只判断“生成了一个文件”不算通过。

文件名可包含目的地、日期和版本，但不包含敏感地址。应用内导出缓存可定期清理；用户已下载到其他位置的文件不应随旅行删除而被扫描删除。

## 21. 测试策略

### 21.1 谁来做、怎样做

开发 AI 自己安装必要工具、准备独立测试数据、启动应用、运行测试、读取结果、修复失败并再次运行。用户观察页面只提供体验反馈，不负责判定 API、数据库或测试命令是否成功。

测试按风险选择：时间/金额/日期需要单元测试；存储、服务适配和版本提交需要集成/API测试；关键用户流程需要浏览器测试；视觉调整需要截图和人工智能视觉检查。小文案修改不为凑指标新建一堆测试。

每个开发阶段都需要适用的类型检查、静态检查、生产构建与实际启动验证；根据影响范围回归已完成能力。通过后不无理由反复跑相同全量检查。

### 21.2 两条验证线

**可重复逻辑验证：** 固定时钟、固定票据、已知地图结果、模拟失败，用于精确验证计算和异常。这些数据必须标记为测试数据。

**真实服务验证：** 使用作者配置的实际服务，验证本阶段真正使用的调用，例如地点查询、公交路线、图片输入，而不只测试“能回答你好”。记录调用时间、能力、结果摘要，隐藏密钥和个人信息。

模拟通过不等于真实通过；实时数据发生变化也不应导致精确计算用例随机失败。两者报告分开。

### 21.4 最终真实演练

至少一条完整真实链：自然语言 → 实际 AI 理解与生成 → 实际地点/路线与来源 → 保存重开 → 实际票图识别及确认 → 红线 → 重规划 → 执行模式 → 四种导出。

票据可以使用明确标注的人工测试票面，通过真实识别服务；这验证识别流程，不证明真实购票或旅行发生。不可用的实时票务信息继续按产品边界标待确认。

### 21.5 证据要求

每阶段保存实际测试名称、运行时间、环境/版本、成功或失败摘要、必要截图、生成文件和修复后的复测记录。真实服务证据只保留脱敏元信息。

屏幕截图要来自实际运行页面；完整 PDF 需要逐页渲染检查。没有浏览器或渲染能力时，不能只读代码就写“UI 已验收”。另一个 AI 可独立复核高风险计算和关键页面，但不以第二个模型的口头同意替代测试。

## 22. 验收策略

### 22.1 阶段结论只有三种

| 结论 | 含义 | 能否宣布阶段完成 |
|---|---|---|
| 通过 | 本阶段所有要求和 DoD 有真实证据，重要缺陷已修复 | 可以 |
| 不通过 | 存在未达标功能或失败测试，AI 继续修复 | 不可以 |
| 外部条件待验收 | 例如缺真实 Key、服务不可达、没有合法地图导出能力 | 不可以；记录具体条件，不能将模拟通过冒充阶段通过 |

对第三种状态，AI 先完成当前阶段可独立进行的实现、模拟验证和问题定位，再说明作者需要提供的最少信息。此时不进入依赖它的后续阶段，也不要求作者自己调试。

“无实时余票服务”是事先定义的产品边界，可按诚实展示验收；“地图接口从未测通”是核心实现未完成，不能混淆两者。

### 22.2 阶段验收门槛

功能入口真实可用；应用启动和构建通过；新增数据确实保存；外部服务实际能力已测；失败状态可恢复；敏感信息不泄露；改动没有破坏已通过的核心流程。

每个阶段仅在本阶段需要时运行相应测试，不能机械要求所有页面都写单元测试，也不能以“只是个人项目”为由跳过红线、预算和数据一致性的测试。

### 22.3 缺陷分级

- 阻断：数据丢失/泄露、错误关键日期或红线、擅自改变票据、关键流程无法完成、虚假核验。必须修复。
- 重要：地图选错事件、预算重复计费、重规划模块不一致、导出丢关键内容。必须修复。
- 轻微：不影响主要操作的间距、文案或装饰问题。记录并在适合的打磨阶段处理，不无限拖延。

### 22.4 最终第一版验收

F01—F28 全部有对应实现与通过证据；T01—T32 按适用环境完成；未选用的部署模式明确写“未选择/未验证”。完整 PDF、地图、红线、重规划等用户指定功能不能作为轻微问题跳过。

AI 出具简短验收结论和完整证据记录，并提供网页入口、可点击启动方式、数据位置、备份恢复和日常设置说明。用户可以继续反馈“不好用”，技术验收无需用户签字或查看代码。

## 24. 每阶段详细任务

每阶段使用相同的十二项模板。下文 DoD 均包括第 25 章的通用门槛；“测试”列举 AI 实际需要执行的检查，不把要求转交给作者。

### 阶段 0：可以启动的项目骨架

#### 目标
建立最小、稳定、可以由 AI 启动和检查的应用。

#### 用户能看到什么
AI 打开一个本地网页，显示项目名称和简洁欢迎内容。

#### 功能要求
检查 Windows 环境和兼容依赖；创建最小 Next.js/TypeScript 项目；服务能启动、停止、再次启动。初始化版本记录和简短项目状态文件，由 AI 管理。

#### 页面
最小首页。

#### 交互
用户只需打开 AI 给出的真实地址；本阶段无旅行规划按钮。

#### 数据
只保存项目配置和开发记录；不预建未来业务表。

#### 技术实现
AI 安装必要运行环境，锁定依赖，建立必要目录和错误页面；检查端口占用，避免覆盖现有文件。

#### 测试
AI 实际启动网页、访问并检查页面；运行类型/静态检查与生产构建；停止后再次启动。静态骨架不额外写无意义单元测试。

#### 验收标准
真实地址可访问，页面无运行错误；重启成功；不依赖用户手动执行命令。

#### 常见失败情况
依赖不兼容、端口被占、目录权限不足、启动只在一次临时终端有效。

#### Definition of Done
通用 DoD 通过，保存环境版本、实际访问地址、构建和启动证据。

#### 本阶段不做什么
不接 AI、数据库、地图、登录、导出；不创建未来空模块。

### 阶段 1：旅行产品首页

#### 目标
建立温暖、清晰的旅行产品视觉入口。

#### 用户能看到什么
具有旅行氛围、清楚说明产品价值的首页，手机也能舒服阅读。

#### 功能要求
按第 9 章实现排版、颜色、图片、空状态与基础组件；明确区分展示用样例与个人旅行。

#### 页面
首页。

#### 交互
只开放当下有实际结果的操作，例如查看样例内容；尚未实现的规划操作不做成可点击的假功能。

#### 数据
少量明确标注的样例内容和有许可的首页图片信息。

#### 技术实现
集中定义必要的样式令牌，按需引入组件；优化首页图片大小。

#### 测试
AI 查看桌面、平板和手机宽度截图；检查键盘焦点、文字对比、图片失效与页面无横向溢出。

#### 验收标准
视觉符合旅行产品方向，信息层级清楚，样例不冒充 AI 实时生成；目标宽度均可读。

#### 常见失败情况
首页变成聊天机器人、过度装饰、小字过多、图片加载撑坏布局、按钮无结果。

#### Definition of Done
通用 DoD 通过，实际截图经 AI 检查，首页资源来源有记录。

#### 本阶段不做什么
不实现需求提取、计划生成、地图与后台。

### 阶段 2：一句话创建旅行草稿

#### 目标
让用户用自然语言开始并修改旅行需求。

#### 用户能看到什么
输入一句话，提交后看到保留原话的旅行草稿。

#### 功能要求
支持多行中文、粘贴、示例填入、编辑和重新提交；空白及过长输入有中文反馈。初始输入上限可设 3,000 字并说明。

#### 页面
首页输入区和简单草稿区。

#### 交互
输入 → 提交 → 查看原话 → 修改；提交后有明确状态，防止连续点击生成重复草稿。

#### 数据
原始文本、临时草稿标识、更新时间；本阶段尚不承诺重启保存。

#### 技术实现
完成表单状态、输入校验和最小草稿流，不用关键字拼凑假 AI 理解。

#### 测试
正常短句、复杂中文、空格/换行、超长内容、快速双击与修改后再提交；检查无输入丢失。

#### 验收标准
用户原意与文本完整保留，反馈清晰，没有虚假的“AI 已生成行程”。

#### 常见失败情况
刷新丢失却显示已保存、输入法回车误提交、重复提交、超长输入导致页面卡死。

#### Definition of Done
通用 DoD 通过，输入主流程与异常在浏览器实际走通。

#### 本阶段不做什么
不解析旅行字段、不调用 AI、不建立复杂需求表单。

### 阶段 3：保存和管理旅行

#### 目标
让一趟旅行真正保存在本机，之后能继续使用。

#### 用户能看到什么
“我的旅行”列表；关闭网页和应用后还能找回草稿。

#### 功能要求
创建、保存、打开、改名、修改原话、继续编辑和删除；显示保存状态，删除确认。后续字段扩展必须沿用同一旅行记录。

#### 页面
我的旅行、草稿详情。

#### 交互
保存后进入列表；打开继续；修改后保存；删除前确认对象名称。

#### 数据
Trip 最小表、原话、标题、状态、创建/修改时间。

#### 技术实现
SQLite/Prisma、稳定数据目录、最小数据库迁移和独立测试数据库；保存接口校验输入。

#### 测试
AI 测试 CRUD 接口，保存后刷新、关闭服务再启动；同时保留两趟旅行并只删除其中一趟；模拟写入失败。

#### 验收标准
成功保存的数据重启后仍存在；失败不显示已保存；操作不误改其他旅行。

#### 常见失败情况
数据写进临时目录、仅存在页面内存、删除范围错误、无权限或空间不足导致假保存。

#### Definition of Done
通用 DoD 通过，数据库持久化和两趟旅行隔离得到实证。

#### 本阶段不做什么
不做账号、云同步、复杂搜索和未来数据表。

### 阶段 4：通过网页配置 AI 服务

#### 目标
用户能够不改代码地连接和更换 AI 服务。

#### 用户能看到什么
密码保护的个人设置页，保存服务信息并看到真实连接结果。

#### 功能要求
首次密码设置；Provider、Base URL、Key、模型、测试连接、保存；高级选项提供基础/系统 Prompt 编辑和恢复默认。失败保留旧配置。

#### 页面
个人设置与密码验证。

#### 交互
用户在页面输入自己的配置；点击测试后保存；AI 负责诊断错误与验证。密钥不通过聊天索取。

#### 数据
密码哈希、加密配置、Prompt 内容/版本、连接状态摘要；不保存聊天式测试全文。

#### 技术实现
服务端适配器、会话保护、受控网络请求和脱敏记录；远程模式复用单一密码全站保护的配置边界。

#### 测试
真实文本连接；错误 Key、模型不存在、超时、无响应、未登录调用设置接口；确认浏览器读取不到秘密；Prompt 保存和恢复。

#### 验收标准
实际配置可用于真实请求；更换服务无需编辑文件；敏感写入受保护。

#### 常见失败情况
前端暴露 Key、测试成功但未保存、保存错误地址破坏原设置、仅用模拟响应冒充连接。

#### Definition of Done
通用 DoD 及真实文本连接通过；缺真实服务条件时不能宣布完成。

#### 本阶段不做什么
不做完整后台、多管理员、用户系统或预接地图/搜索。

### 阶段 5：AI 理解需求与必要追问

#### 目标

把原话转成用户能确认的旅行条件。

#### 用户能看到什么

目的地、具体日期、人数、预算、节奏等摘要；缺关键内容时只问必要问题；修改后清楚显示需要重新确认。

#### 功能要求

提取第 11 章需求字段；处理相对日期、预算口径、2～4 天限制和冲突；摘要可编辑。TripRequest 从本阶段引入 requestRevision；所有影响规划的需求编辑，包括沿用阶段 03 修改原话的入口，保存时递增修订并清除确认。确认只绑定当前已保存修订，后续生成只能使用该修订的确认需求。

#### 页面

需求确认区。

#### 交互

输入原话 → 查看理解 → 回答 1～3 个关键问题 → 修改并保存 → 确认当前修订；再次修改即回到待确认，不强迫补全所有可选偏好。旧页面的确认请求不能确认后来修改的内容，未保存编辑也不能沿用旧确认。

#### 数据

TripRequest 的原话、提取结果、字段来源、默认假设、待确认项、requestRevision、确认所对应修订和最终确认需求；已有草稿在本阶段补齐修订状态，不凭旧记录推定新修订已获确认。

#### 技术实现

真实模型结构化输出或 JSON 降级路径，Schema 校验，有限修复，固定时钟测试。保存需求和确认均核对当前修订；提取请求捕获启动时的 requestRevision，返回时检查该修订及请求仍有效，旧结果不得覆盖已修改输入；页面有未保存编辑时也不以迟到响应覆盖。提取只产生待确认草稿，接纳结果也遵循统一需求保存规则，修订递增与清除确认一并保存；用户确认后，该轮未完成的提取请求失效。

#### 测试

T02；完整示例、缺目的地、过去日期、跨月周末、多人口径、超出天数、模型拒绝/畸形输出；修改原话/摘要/追问答案后修订递增并失去确认，过期确认及提取响应被拒绝，未保存编辑不被旧提取回填覆盖。本阶段只验需求修订、确认与提取保护，不测试尚未实现的生成界面。

#### 验收标准

不会默猜精确地点；日期与口径可见；用户纠正后保存的是纠正结果；真实理解接口已走通。只有当前已保存修订能被确认，任一需求编辑入口都不能绕过修订递增与重新确认，迟到提取不覆盖新输入。

#### 常见失败情况

无限追问、遗漏预算单位、原话与摘要冲突、把不存在日期或假设当确定事实；修改原话仍沿用旧确认、旧提取覆盖用户纠正、旧页面确认了新修订。

#### Definition of Done

通用 DoD 通过，测试集覆盖提取、追问、修订与确认、旧响应保护和失败恢复；阶段 03 的修改原话入口已纳入同一规则。

#### 本阶段不做什么

不生成完整日程、不接地图、不让用户阅读 JSON。

### 阶段 6：生成基础旅行计划

#### 目标

将确认需求变成结构完整的可阅读行程草稿。

#### 用户能看到什么

按日列出的去返程、住宿区域、餐饮、活动、时间和准备事项。

#### 功能要求

仅以当前已确认需求修订生成 2～4 天基础安排；保留用餐、交通和休息；检查时序、固定约束和字段完整；暂无实时依据的信息明确标估算/待确认。同一基础生成入口可在确认新需求后生成新计划版本；更新已有计划时，须保留当时已引入的有效票据、锁定安排和已发生事实，需求改动不能解除这些约束。

#### 页面

基础行程预览。

#### 交互

确认当前需求修订后点击生成、查看实际进度、取消或失败重试；生成期间需求或当前计划版本变化时，旧结果不得提交，提示基于当前状态重试。修改需求后旧计划只标待更新，仍按自身需求快照展示；失败不覆盖已有计划。

#### 数据

从本阶段建立 PlanVersion，保存版本号、requestRevision、requestSnapshot（该修订经用户确认的完整需求快照）、事件、地点名称、建议时长、费用草稿、待核验项和校验结果；requestSnapshot 是固定副本，不能被最新 TripRequest 覆盖。后续原计划展示、编辑校验、预算与导出均沿用该计划自身快照。

#### 技术实现

单次受控规划调用、业务校验、短事务保存；请求捕获已确认的 requestRevision 和当前计划版本 V（包括首次生成时无计划的状态）。提交时在短事务中同时核对需求修订仍相同且已确认、V 仍为当前，并校验当时已引入的约束后一次提交；任一冲突都拒绝旧结果，不能只检查计划版本，也不能在提交时给旧输出补上最新 requestRevision。不让 AI 直接返回整页 HTML。

#### 测试

2 天/4 天样例；超低预算、重叠时段、负耗时、缺返程、格式错误、重复点击、取消和请求中断；T29 的本阶段适用部分：生成期间分别修改目的地/日期/人数，即使重新确认，旧需求结果仍拒绝提交，旧计划预览和保存快照保持原依据。导出验收留到相应阶段，不预建入口。

#### 验收标准

基础计划完整可存并能追溯所用需求修订与确认快照；没有无依据的确切余票/价格；不可行草稿被明确指出；应用仍可按原依据打开旧版本。未确认或已过期的需求结果不能提交，需求与计划两类版本任一变化都不能被旧请求覆盖。

#### 常见失败情况

只生成攻略文章、忘记返程、活动密度过高、出错写入半份数据；只检查计划版本、旧请求借新确认提交、把新需求写进旧计划快照、借需求修改解除已有硬约束。

#### Definition of Done

通用 DoD 通过，真实模型返回经校验形成一个带需求修订与确认快照的完整保存版本，需求/计划双版本保护及 T29 适用部分通过。

#### 本阶段不做什么

不做正式地图、精美推荐卡、红线或导出，不提前实现阶段 22 的重规划界面或阶段 28 的数据代际模块；不能把本阶段称为完整 MVP。

### 阶段 7：旅行结果总览

#### 目标

让用户一眼看懂生成结果，并找到日程与待确认事项。

#### 用户能看到什么

旅行标题、该计划依据的日期/人数/节奏/预算目标、每日主题和待办概况；最新需求有改动时提示当前计划待更新。

#### 功能要求

统一展示当前计划版本；组织日期导航和已实现模块入口；摘要与详情来自同一 PlanVersion，日期、人数、节奏和预算目标等需求依据读取其 requestSnapshot。编辑最新需求后只标当前计划待更新，不把新需求混入旧计划；确认新需求并由阶段 06 入口提交新版本后才切换依据。此时只显示该计划的预算目标和费用待核算提示，阶段 9 再接入程序计算的费用摘要。

#### 页面

旅行详情总览、窄屏对应布局。

#### 交互

切换日期、查看每日内容、回到阶段 05 需求修改/确认流程、返回旅行列表；修改后保留旧计划及其待更新提示，复用阶段 06 的生成入口形成新版本；不显示尚不可用的地图/导出按钮。

#### 数据

复用 PlanVersion 及其 requestRevision、requestSnapshot，不新建总览数据副本；最新 TripRequest 仅供需求编辑与修订差异判断，不能作为旧计划展示数据的补丁。

#### 技术实现

共享读取与格式化函数，完成加载/空状态/错误状态；比较计划所用 requestRevision 与最新需求修订来显示待更新状态，规划依据始终读取所展示计划的 requestSnapshot。

#### 测试

有计划、无计划、旧草稿、长城市名、四天切换、刷新重开；检查总览与计划保存值一致。覆盖 T29 的总览适用部分：修改目的地/日期/人数后，旧计划各处仍展示原快照且标待更新，重新确认本身不改变旧计划；阶段 06 新版本提交后总览才整体切换。

#### 验收标准

无需读长文即可了解旅行框架；未确认项可发现；没有版本错配或无效入口。最新需求变化不会改变旧计划的日期、人数、节奏或预算目标，待更新提示明确，生成新版本后摘要与详情一同切换。

#### 常见失败情况

把预算目标称为预计总费用、日期切换只更新半个页面、把过期计划伪装为新结果、旧行程配上最新需求的日期/人数/预算目标。

#### Definition of Done

通用 DoD 通过，桌面/手机截图和结果浏览流程完成，需求修改后的旧计划快照一致性及新版本整体切换得到验证。

#### 本阶段不做什么

不实现地图、红线、深度推荐或新的 AI 调用路径；需求确认和基础生成仅复用阶段 05/06 已有能力。

### 阶段 8：每日时间轴

#### 目标

用连续时间轴组织每天行程，并支持基础编辑。

#### 用户能看到什么

每天什么时候做什么、上一项如何接到下一项；可修改时间、时长、备注并锁定重要安排。

#### 功能要求

按日期排序，区分活动和交通；支持跨日；允许编辑、移除非固定活动和锁定；修改后按所编辑计划自己的 requestSnapshot 执行当前可用的约束检查并保存，继承其 requestRevision。新需求未应用时仍标待更新，不把普通编辑改标成已采用最新需求。后续路线、费用和红线接入同一更新入口。

#### 页面

旅行详情时间轴与简短编辑抽屉。

#### 交互

切换天 → 点事件 → 修改/锁定 → 保存或取消；冲突展示原因，不自动挪动被锁定安排。

#### 数据

事件 ID、日期、顺序、起止时刻、状态、锁定与备注，继承原需求修订/快照的计划新版本。

#### 技术实现

统一日期计算和事件校验；交通展示行不重复占用时间或创建费用。

#### 测试

跨午夜、活动重叠、负时长、锁定后删除、取消修改、改后重开；键盘和手机编辑流程；T29 的本阶段部分：最新需求待更新时编辑旧计划，校验依据和保存后的需求快照保持一致。

#### 验收标准

时间顺序正确；编辑可保存、可取消；固定安排不被静默改动；缺路线时不假称已核实交通可达。

#### 常见失败情况

只按时分排序、日期丢失、拖动导致 ID 变化、酒店整晚记录误占所有活动。

#### Definition of Done

通用 DoD 通过，跨日与编辑冲突用例通过，完整日程能逐项读懂。

#### 本阶段不做什么

不做复杂拖拽编排、地图联动或 AI 重规划。

### 阶段 9：预算

#### 目标

让用户知道预计花多少钱，以及有没有超出预算。

#### 用户能看到什么

总额/区间、交通/住宿/餐饮/门票/城市交通/其他分项，以及确定、预计、浮动状态。

#### 功能要求

支持全程与人均口径；按同一计划版本中的人数、房间和晚数计算，需求依据读取该 PlanVersion.requestSnapshot，费用数量读取该计划快照，不能混用最新 TripRequest；已支付与确定程度分开；允许确认单项金额。下限已超预算提示确定超支，上限超过提示可能超支，缺金额不当零；最新需求变化只标旧计划待更新，不改算其费用或预算目标。

#### 页面

预算页签、总览预算摘要。

#### 交互

查看分类明细、确认当前计划中的已知金额。修改预算目标、人数、房间或晚数等影响规划的需求时，先保存并确认新需求修订，再通过已有阶段 06 基础生成入口形成计划新版本，程序按新版本自身快照重算；新版本提交前，旧计划继续按原依据显示预算。

#### 数据

同一 PlanVersion 内的 CostItem、币种、计价单位、数量、区间、来源和支付状态，以及该计划已有的 requestRevision/requestSnapshot；不另存一份会随最新需求漂移的预算依据。

#### 技术实现

整数分计价、程序汇总、唯一费用关联；交通展示不新增同一笔钱。计算显式接收同一计划及其 requestSnapshot；确认金额等计划编辑沿用统一保存入口并继承原 requestRevision/requestSnapshot，不能借金额编辑混入最新需求。最新需求待确认不阻止保存当前计划的真实金额和已发生费用，旧计划继续标待更新；需求改变后的基础生成仍执行阶段 06 的双版本提交与已引入约束保护。

#### 测试

演示 486＋280＋260＋60＋80＋120＝1,286；多人/多房/多晚、区间、未知、零元免费、退款待处理、重复事件；T29 的预算适用部分：修改人数/晚数或预算目标但尚未形成计划新版本时，旧预算保持原依据；重新确认并经阶段 06 提交新版本后，才按新快照重算。

#### 验收标准

分项与总计一致，口径清楚；无法确定的金额保留估算；已消费不因移除活动而消失。预算人数、晚数、目标和费用均能追溯至同一计划快照；新需求未生成新计划前不改变旧预算，新版本提交后总览和预算整体更新。

#### 常见失败情况

浮点误差、住宿按人重复计算、城市交通同时算两次、删景点自动“退款”、把新需求的人数/晚数/预算目标套到旧计划费用上。

#### Definition of Done

通用 DoD 通过，预算单元/集成用例精确通过，界面与保存值一致；需求修改、重新确认与基础生成后的预算快照切换通过，不提前实现阶段 22。

#### 本阶段不做什么

不做记账系统、支付、实时全网比价或多币种，不另建需求更新用的 AI 重规划模块，不提前实现阶段 22。

### 阶段 10：信息来源与可靠性

#### 目标
用户能够分清已核验信息、用户确认和估算。

#### 用户能看到什么

### 阶段 13：城市路线与方向

#### 功能要求

#### 页面

地图、时间轴交通行、路线详情。

#### 交互

点某段看步骤；切换方式或修改出发时刻后，取得适用于新时刻的路线再更新预计时间和预算，检查后续是否冲突。超出原有效窗口的结果不能继续显示为已核实可用。

#### 数据

RouteLeg、路径折线、步骤、包含的耗时、完整出行日期、适用出发时刻/有效窗口、班次依据、费用和来源；保留候选时刻复核结果及能力限制。

#### 技术实现

地图路线适配、路线缓存、统一时间/费用更新；缓存必须包含完整出行日期及适用出发时刻/有效窗口，并区分地点、交通方式，不能只按同一天复用。需要按新时刻重查时，最多 3 轮候选时刻复核（含首次）；不收敛或缺少未来能力时保持估算或待确认，不宣称精确可执行。检查是否已包含候车换乘，避免重复计时计费。

#### 测试

真实步行/公共交通/驾车查询；无路线、凌晨停运、方式不支持、费用未知、地图超时和路线变更后日程冲突。T28 在本阶段只验证同日不同时刻的班次等待、到达时刻和缓存隔离；补充 3 轮上限及未来能力缺失的降级检查，不执行阶段 15 的红线断言。

#### 验收标准

折线和箭头来自可用数据，文字、班次及适用时刻一致；改变时刻不能错误命中旧路线缓存。缺少未来能力或 3 轮内无法完成复核时有明确降级；失败不画成已核实的直线道路。

#### 常见失败情况

将直线距离当步行、把驾车时长等同叫车全过程、用白天公交套凌晨、同日改时刻仍沿用旧候车耗时、复核无界重试、重复算交通费用。

#### Definition of Done

通用 DoD 及相关真实路线能力通过，T07/T10 和 T28 的本阶段适用部分、时刻缓存隔离及有界降级检查通过；不把后续红线功能作为本阶段已完成能力。

#### 本阶段不做什么

不做车次余票、实时导航、自动叫车或跨城门到门整合；不提前实现阶段 15 的红线倒推、界面或验收。

### 阶段 14：门到门去返程交通

#### 目标

把家门口、车站/机场、目的地和返家串成完整交通链。

#### 用户能看到什么

去程和返程的所有环节，高铁/飞机候选或自己已确认的票面；区分当前有效票、已退票和已替换的历史票。

#### 功能要求

支持高铁/飞机主交通与城市接驳；简短面板录入确认日期、站点、时刻，并确认已办妥的退票或替换指定票事实。只有 active 票参与当前交通硬约束；保留旧票历史与已支付费用，退款须另行用户确认并按阶段09既有费用规则记录，不能因退票/替换自动归零。共享事件按仍 active 的票判断，替换单张不影响其他票；多人不同班次无法用当前单线表达时保存事实并明确冲突。考虑行李、办理与必要缓冲；无准确班次时显示候选时段和官方查询入口。

#### 页面

交通总览、票面确认面板及“已退票/替换指定票”事实确认入口、时间轴和地图。

#### 交互

选择交通方式或录入已购票 → 确认出发/返程地点 → 查看完整链条；用户也可选择指定原票，确认自己已办成的退票或替换事实。替换前核对新票和受影响的原票，确认后才更新；未确认或取消不改当前计划。真实票据可以连同冲突/资料待补状态保存；需求已改但未确认时，用户确认的票据、退票和费用事实仍可记录，旧计划继续标待更新，不为制造可行而改变票面。购票及退改签仍由用户在官方平台操作。

#### 数据

交通事件、手动 Ticket（稳定 ticketId、status=draft/active/cancelled/replaced、confirmedAt、可选 replacedByTicketId）、起点、枢纽、办理条件、固定约束、接驳路线。confirmedAt 保留票面曾经确认的事实，与当前是否有效分开；只有 active 参与当前硬约束，cancelled/replaced 保留历史关联。

#### 技术实现

复用城市路线与票面校验；外部查询放在事务外。确认退票或替换时，一次短事务核对当前计划等适用版本，同步真实票据/费用事实、新计划版本及已引入的约束/事件/路线/时间，并使旧派生结果失效；替换必须同时将新票设为 active、指定旧票设为 replaced 并关联 replacedByTicketId，退票将指定票设为 cancelled。事实更新继承当前 PlanVersion 自己的 requestSnapshot 与 R（生成所用需求修订），需求已改未确认时保留旧计划待更新标记，不能改标成采用最新需求。路线查询失败也要原子保存已确认事实和失效/待重算或冲突状态，不能因缺路线忽略真实退票；数据库提交失败则保留原状态。跨城无轨迹只画示意；检查飞机值机/托运/登机条件，保留待确认状态。

#### 测试

高铁链、国内航班链、返程末班接驳、不同航站楼/站点、次日到达、未购票、自驾费用缺失和无法衔接；T30：有效票确认退票、替换指定票、两张同行票只替换一张，核对 active 约束、共享事件、已支付费用和退款确认；另测需求已改未确认或路线查询失败时仍保存真实事实并使旧派生内容失效，及版本冲突/保存失败无半更新。本阶段只验已引入模块，不要求提前验阶段15红线。

#### 验收标准

去返程均从出发点连到最终返回点；无遗漏接驳；确认票不被静默更改，仅 active 票生成当前交通约束。退票/替换后旧票历史与已支付费用保留，其他有效同行票不受影响；无法衔接时如实保存事实并标冲突或待补，不沿用失效路线，不虚构实时余票。

#### 常见失败情况

只有城市名之间一条线、忘记出站/进机场、返程到站后没有回家、把参考班次当已购票；已退/已替换票仍生成约束、替换一张却停用同行票、旧费用自动清零，或因资料不足拒绝记录用户已确认的真实票据。

#### Definition of Done

通用 DoD 通过，至少高铁和飞机各完成一条可解释的全链演练；T30 在本阶段已引入模块的约束、费用、共享票和失败原子性检查通过，阶段15红线留到引入后验证。

#### 本阶段不做什么

不识别截图、不计算正式红线、不自动购票/退票/改签/预订，不扩展多人分路架构；退票/替换入口只记录用户已办成的事实。

### 阶段 15：时间红线

#### 目标

让用户知道最晚什么时候该行动，以及当前是否还来得及。

#### 用户能看到什么

突出的出门/返程红线、倒计时、缓冲明细和冲突原因。

#### 功能要求

按第 15 章实现多截止点倒推、去返程和跨日，分开硬截止与建议。固定耗时可直接倒推；有班次或时刻相关路线必须按适用时刻选择候选，从倒推得到的建议出发时刻正向复核所有截止，不能只从当前时刻检查；同时保留从真实当前时间出发的可行性检查。可在详情调整行李、首次到访、步行和额外缓冲。

#### 页面

总览红线条、时间轴、红线详情。

#### 交互

展开计算依据和路线适用时刻；修改起点/票/偏好即重算。需要按新时刻重查时最多 3 轮候选时刻复核（含首次）；不收敛或缺少未来能力时显示估算或待确认，不宣称精确可执行。过建议时间或无法衔接时给出明确状态。

#### 数据

截止依据、步骤耗时、缓冲原因、建议时刻、路线适用日期/时刻/有效窗口、候选时刻及复核轮数、各截止的复核结果、计算版本、状态及可见假设。

#### 技术实现

确定性函数计算时间与缓冲，不让模型填写计算结果；函数外查询适用于候选时刻的路线，复用阶段 13 的日期/时刻缓存口径。最多 3 轮候选时刻复核包含首次；超限、不收敛或缺未来能力时降级。总耗时与分项、办理耗时与缓冲均不重复累计；变更统一使旧结果失效。

#### 测试

完整 T09—T12 及 T28；增加缓冲应相应提前，路线已含换乘不再扣；多航空截止、未知截止、红线在前一天。覆盖当前时刻可行但倒推时刻错过班车、改时刻后缓存失效、最多 3 轮复核，以及不收敛/无未来能力时的估算或待确认状态。

#### 验收标准

08:55 和前一天 22:55 用例精确通过；T28 的错误候选 09:05 必须被拒绝为可执行红线。建议出发时刻与真实当前时刻两条正向检查均存在；橙/红边界唯一，所有红线有依据；无法衔接不靠挪票解决，无法完成时刻复核时不宣称精确可执行。

#### 常见失败情况

时区/跨日错、缓冲重复、把一次查询的公交等待时间平移到新时刻、只从当前时刻验证、重复复核没有上限、把估算当官方截止、设备返回前台倒计时不更新。

#### Definition of Done

通用 DoD 通过，全部红线关键用例及 T28、3 轮上限/降级检查必须通过；交接可重跑的时刻相关输入与独立预期，不允许作为轻微问题放行。

#### 本阶段不做什么

不做后台通知、闹钟、自动改签或“保证赶上”的承诺。

### 阶段 16：高铁票截图导入

#### 目标

省去逐项输入票面信息，确认后自动用于行程计算。

#### 用户能看到什么

上传、裁剪、识别预览和确认；加入或确认指定票退票/替换后更新红线，有冲突或资料不足时明确待处理。

#### 功能要求

识别日期、车站、车次、出发/到达时刻及座位；关键字段必经确认；处理缺字段、跨日、疑似重复、同行票和替换票；保护原图隐私。复用阶段14的稳定票据身份与有效状态，仅 active 票参与当前约束；退改截图先作为待确认资料，用户确认已办成的退票/替换事实后才更新指定票。保留旧票历史及已支付费用，退款按阶段09规则另行确认；替换单张不影响其他 active 同行票。

#### 页面

交通页的导入面板、识别确认页及共用的指定票退票/替换事实确认面板。

#### 交互

选图并在发送前裁剪 → 识别 → 修正 → 选择去程/返程、同行票或指定原票的替换 → 用户确认后提交；退票资料也须确认指定原票和已退事实，取消或未确认不修改计划。需求已改未确认时仍可记录用户确认的真实票据/退票与费用事实；有冲突或资料待补时如实保存，不因暂时不可行而改写票面。多人不同班次无法用当前单线表达时保存事实并显示冲突。

#### 数据

临时图、识别草稿、复用阶段14的 Ticket（稳定 ticketId、status=draft/active/cancelled/replaced、confirmedAt、可选 replacedByTicketId）、匿名票数/座位信息、识别来源、去重线索；confirmedAt 表示历史确认，不替代当前有效状态。

#### 技术实现

真实视觉模型或合规 OCR 适配；上传校验、临时清理，外部调用放在事务外。确认/退票/替换共用阶段14短事务：核对当前计划等适用版本，同步真实票据/费用事实、新计划版本与已引入的约束/事件/路线/时间，并将阶段15红线纳入同次失效重算；替换同时写新票 active、指定旧票 replaced 及 replacedByTicketId，退票只将指定票 cancelled。事实更新继承当前 PlanVersion 的 requestSnapshot/R，需求已改未确认时不冒充采用最新需求，旧计划仍待更新。共享事件依仍 active 的票判断；路线查询失败仍须原子保存已确认事实与旧派生结果失效/待重算或冲突状态，旧路线和红线不得冒充有效；数据库提交失败不留下半更新。

#### 测试

T13/T14/T26；模糊/旋转/缺年份/次日到达/退改票、重复截图、同行不同座位、无金额、确认前取消；T30：有效票确认退票、替换指定票、两张同行票只替换一张，核对有效约束、共享事件、费用与红线失效重算；需求已改未确认或路线查询失败时仍记录真实事实并使旧派生结果失效，版本冲突/保存失败时无半更新。

#### 验收标准

真实服务能识别正常样本；用户确认前不生效；去重不漏同行费用；导入后红线与手动输入一致。仅 active 票生成当前约束，T30 中指定原票状态、同行票、费用和红线结果正确；资料不足或多人班次冲突时仍保留事实并明确待处理，失效路线/红线不显示为可执行。

#### 常见失败情况

把深圳站认成深圳北、缺到达时间时胡编、识别成功即标全票官方核验、原图泄漏；把退票截图当有效票、已退票仍产生红线、替换单张时改坏同行票、旧费用自动清零或新旧票只更新一半。

#### Definition of Done

通用 DoD、真实识别路径及 T30 含红线的状态/费用/失败回归通过；仅手动录入或模拟识别不能作为本阶段通过。

#### 本阶段不做什么

不做机票截图专项识别、自动购票/退票/改签、证件提取或永久票据相册，不扩展多人分路架构；只记录用户已办成并明确确认的票据变化事实。

### 阶段 22：AI 重新规划

#### 目标

用一句话调整剩余旅行，保持已确定事项和模块一致。

#### 用户能看到什么

“下雨了”“晚起一小时”“不去这个景点”后得到可应用的新方案与变更摘要。

#### 功能要求

以当前已确认需求修订 R 生成剩余行程，只改未完成部分；保留当前 status=active 的票据、固定预约、已完成活动、用户锁定和已发生费用，draft/cancelled/replaced 票据不参与硬交通约束。重算餐厅/路线/时间/预算/红线/清单；应用时再次检查当前时间与已读版本，不能只凭预览时可行就提交。下雨、迟到等仅改变情境时复用已有需求确认；确实修改目的地、日期、人数等需求字段时，先走阶段 05 同一修订确认流程，不能偷偷改写 requestSnapshot。

#### 页面

详情的调整输入、方案对比与确认区。

#### 交互

输入变化 → 查看取消/替换/时间及预算影响 → 应用或取消。点击应用后读取最新时钟并复核；现在已赶不上就拒绝应用。复核导致活动、计划时刻、路线或费用实质变化时重新展示预览，再由用户选择应用，不能静默提交变化后的方案。可撤销到上一安排，但须重新检查当前时间及有效约束，已发生事实不能回退。

#### 数据

候选所用 requestRevision/requestSnapshot、基础计划版本、当前已引入的清单/事件状态版本及执行状态版本（仅已引入时）、变更原因、候选完整快照、核验时刻与可行性有效窗口、校验结果、最新版本与上一版。新 PlanVersion 保存候选实际使用的已确认需求修订和快照。

#### 技术实现

受控 AI 提议、程序校验及原子提交。应用时读取最新时钟，核对候选的需求修订 R 和基础计划版本；R/V 已变则拒绝旧候选，不能临提交给它补写最新 R/V。重新读取并保护已引入的清单/事件及执行状态，复用阶段 15 的时刻相关路线复核；需要重查路线时放在事务外，最多 3 轮候选时刻复核（含首次），不收敛或缺少未来能力时保持估算或待确认，不宣称精确可执行。提交前短事务比较所有已读版本，确认 R 仍为当前且已确认的修订，并读取当前时钟检查可行性窗口仍有效；事务内不调用外部服务。不冻结红线本身，它必须按适用路线重算。

#### 测试

T16/T17/T31，并回归 T28 的时刻相关路线复核；下雨、迟到、删点、固定返程已不可行、生成中改需求/改票/改已有状态、取消/超时、保存失败、撤销。T31 仅推进时钟而保持所有版本不变；另测复核后内容实质变化需重展示、提交前窗口过期及事务内无外部查询。下雨/迟到不要求重复填写已确认需求；取消/替换票不进入硬交通约束。

#### 验收标准

三个正常重规划样例均可应用且各模块读取同一新版本；旧候选不能借补写最新 R/V 通过，当前有效票据与已发生事实不被偷偷改变。T31 中即使版本未变化，当前已不可行的候选也必须拒绝应用；实质变化先重新展示，提交时仍需满足时间窗口和版本检查。失败完整保留已有计划与最新真实状态。

#### 常见失败情况

重新生成整趟并丢进度、拿旧 requestSnapshot 冒充当前需求、给旧候选补最新版本、冻结已取消票、把返程延后制造可行、预览搁置后只查版本不查当前时间、重查改了路线/费用却直接提交、事务内等待外部查询、清单全清零、地图新版预算旧版。

#### Definition of Done

通用 DoD、真实重规划流程、当前需求/有效票据保护、并发/失败用例及 T31 通过；应用时钟复核、实质变化重展示和提交前窗口检查有独立证据，无半提交状态。

#### 本阶段不做什么

不自动退改票、不创建多 Agent、不做无限方案树和复杂历史系统；不提前实现阶段 23 执行界面/专门执行状态，也不提前引入阶段 28 的 dataGeneration。

### 阶段 23：旅行执行模式

#### 目标
旅行中快速回答“现在该做什么、下一步是什么、还有多久”。

#### 用户能看到什么
当前时间、当前位置或预计位置、下一步行动、交通指引与下一条红线。

#### 功能要求
当前步骤可手动选择并标记到达/完成；进度保存；定位可选，拒绝仍能用；进入前台刷新倒计时，区分未来、正在进行和已过期状态。

#### 页面
执行页；手机底部行程/地图/清单/预算/更多。

#### 交互
开始旅行 → 看下一步 → 标记当前进度；发现迟到可进入重规划；退出执行模式不删除记录。

#### 数据
ExecutionState、真实/手动/预计位置来源、完成时间、修改版本，不持续保存完整轨迹。

#### 技术实现
共享时钟与红线逻辑；浏览器定位只在用户选择且安全环境可用时调用；优先手动进度，避免时间推断覆盖实际状态。

#### 测试
T20；未开始/已结束、定位拒绝、长时间后台、手机刷新、断网、设备时间偏差、所有活动完成、进度与重规划并发。

#### 验收标准
不把推测地点称为真实定位；手动模式完整可用；红线不会过期还显示充裕；手机主操作便捷。

#### 常见失败情况
强制定位才可用、锁屏后倒计时错误、进度未保存、宣称浏览器关闭仍会准点提醒。

#### Definition of Done
通用 DoD 通过，执行页真实浏览器演练完成，明确所选运行方式的可达性。

#### 本阶段不做什么
不做持续后台定位、系统闹钟、原生应用和完整道路导航。

#### 常见失败情况

### 阶段 28：备份与恢复

#### 目标

让作者能保留旅行数据，并在升级或换电脑后恢复，恢复前的旧请求不能覆盖恢复后的数据。

#### 用户能看到什么

“下载旅行备份”和“从备份恢复”，能预览备份包含多少趟旅行及影响范围；恢复中显示写入暂停，旧页面提示重新载入后再操作。

#### 功能要求

一致性备份需求及修订、计划版本及生成依据快照/绑定修订、票面必要字段和有效状态、清单、执行状态与来源；排除密钥、登录会话、原图及运行实例的 dataGeneration/恢复屏障。先校验文件并预览影响，用户确认后建立持久恢复屏障，暂停业务写入，在屏障内制作一致性安全副本再改旅行数据；恢复成功或屏障内失败经保护/回退后，都须持久换代才重新开放写入，管理员和服务配置保留。本阶段起技术恢复/回退也执行同一屏障与换代协议。

#### 页面

设置中的数据管理，包含恢复摘要、影响范围和恢复/回退状态；业务写入入口在恢复期间显示暂停原因。

#### 交互

下载备份；选择备份后看内容摘要及影响范围，明确确认再恢复；校验失败只给出原因，不进入恢复。恢复期间暂停写入，可保留只读状态展示；成功后重新读取业务状态，旧页面和旧候选不能继续直接提交。失败时先保护原数据或回退，完成恢复处理后再开放操作；未完成时保留可恢复说明。

#### 数据

有格式版本的旅行数据备份、恢复记录、恢复前一致性安全副本；持久的运行实例元数据 dataGeneration、恢复屏障及恢复进度。实例元数据不进入旅行备份，也不随网页或技术恢复/回退还原；普通重启保留持久代际，未完成恢复另走恢复处理。页面加载和请求开始时捕获 dataGeneration，它与既有 requestRevision、计划/清单/执行修订共同用于提交检查。

#### 技术实现

首版用结构化单文件备份旅行数据，按 Schema 校验；图片许可资料和来源保留，不要求打包所有导出缓存。用普通业务函数和短事务回补全部既有业务写入、生成保存、候选应用、导出登记入口：即使允许只读展示，全部业务提交事务仍须重新检查恢复屏障、捕获的 dataGeneration 及已有业务修订。网页和技术恢复/回退均在屏障持久化后先制作并验证一致性安全副本；成功时在替换旅行数据的同一短事务中换新 dataGeneration 并解除屏障。屏障建立后的失败须先确保原数据完整或回退，再持久换代并解除屏障；保护、回退或换代未完成则保持屏障。进程重启先识别未完成恢复，完成安全恢复或回退并换代后才开放写入，不得直接清屏障；普通重启保留已有代际。拒绝旧请求后必须重读业务状态，不能只补最新代际重发旧载荷；旧候选和在途结果不得作为当前有效结果落盘。外部调用一律在事务外，代际检查不替代已有需求和业务版本检查。

#### 测试

正常恢复、空备份、损坏/旧版/恶意内容、恢复中失败、磁盘不足；恢复后核对旅行数、费用、事件、清单、进度与管理员配置。T32：V5 请求在途→恢复 V4→新编辑再次到 V5→旧响应返回，必须因 dataGeneration 不同而拒绝；另测旧页面写入、旧候选应用、旧导出登记、屏障建立时的在途提交，以及安全副本/替换失败和进程中断后恢复或回退的换代边界；技术恢复/回退同样换代，普通重启保留代际。

#### 验收标准

失败不覆盖当前数据；恢复能重新打开旅行并重算，管理员和服务配置不被替换；文件不包含服务秘密或实例元数据。恢复屏障覆盖所有业务提交，成功、屏障内失败或进程中断处理后均先持久换代再开放写入；旧请求即使业务版本重新相同也不能覆盖恢复后的数据，旧页面须重读，作者无需操作数据库。

#### 常见失败情况

直接替换带密钥的数据库、用导出 PDF 冒充可恢复备份、恢复只剩标题、升级先删库；安全副本完成前仍允许业务提交、dataGeneration 随备份回退、只换最新代际重发旧载荷、失败或重启后未处理恢复屏障就开放写入。

#### Definition of Done

通用 DoD 通过，完成一次备份→独立环境恢复→关键数据比对及失败回退；T32 的版本重用、旧页面/候选/导出登记、屏障竞争、失败和进程中断用例通过，技术恢复/回退遵循同一协议，全部既有提交入口已纳入恢复保护。

#### 本阶段不做什么

不做云同步、跨设备自动合并、企业灾备和永久票图存储，不为恢复引入队列或复杂锁服务；不以 dataGeneration 替代已有 requestRevision 和计划等业务修订。

### 阶段 29：日常启动与选定运行方式交付

#### 测试
正常/重复启动、停止重开、重启电脑后的入口、端口被占、数据目录权限；远程如已选，测外网、登录保护、服务重启后持久化与数据迁移。

#### 验收标准

必须保持开发终端不关闭、重启变空库、公开地址无密码、用短期隧道当长期部署、两实例误认为自动同步。

#### Definition of Done
通用 DoD 及 T24 通过，交付已验证入口和数据保护说明；选远程却未验证不能以本地成功代替。

#### 本阶段不做什么
不购买未授权服务、不添加账号系统、同步、容器集群或复杂持续部署。

## 25. 每阶段 Definition of Done

### 25.1 通用门槛

每阶段详细任务中的专属 DoD 与以下要求同时满足，才允许宣布通过：

1. 本阶段功能达到“用户能看到什么”和验收标准，入口真实，未实现功能没有假成功表现。
2. AI 已实际运行本阶段流程；类型检查、适用静态检查、生产构建和启动验证通过。
3. 适合风险的测试实际执行，失败已修复复测；影响到的旧能力已回归。
4. 新增持久数据经过刷新/重开/重启验证；当前用户数据没有被测试或迁移破坏。
5. 新接或本阶段改变的真实服务路径经过实际验证；模拟测试和真实结果分开记录。
6. 正常、空白、加载与主要失败状态可理解，重试/取消/重复提交不会损坏原数据。
7. 时间、金额、来源、固定约束和跨模块版本满足本文规则。
8. 桌面与手机相关界面经实际检查；状态不只靠颜色，主要操作可访问。
9. 密钥、票面隐私、上传、外部来源和导出没有本阶段引入的泄漏风险。
10. 不存在阻断或重要缺陷；轻微问题具体登记，不以追求完美阻塞下一阶段。
11. 更新开发进度、验收证据、已知边界和下一阶段入口。
12. AI 明确给出“通过/不通过/外部条件待验收”。只有通过才更新已完成阶段。

不适用项由 AI 简短说明原因，例如阶段 1 没有新增数据库，不需要存储迁移测试。不能将缺少真实 API 或没有检查页面解释为“不适用”。

## 26. 风险与解决方案

| 风险 | 最小应对措施 | 何时处理 |
|---|---|---|
| 第一版功能多，长期停留在半成品 | 31 个小阶段，阶段通过即保持可运行，里程碑不冒充终版 | 全阶段 |
| 外部服务账号/地区/额度不可用 | 提前真实能力检测；只选一家有效实现；如实记录缺条件 | 首次接服务时 |
| 模型格式正确但事实错误 | 结构校验加业务校验，外部核验与字段来源分离 | 5、6、10 |
| 时间红线导致误导 | 逐段程序计算，截止与建议分开，说明假设，关键边界必测 | 14—16 |
| 预算漏项或重复 | 唯一费用关联、整数分、计价单位、确定/支付状态分开 | 9、14、16 |
| 地图坐标或站点错误 | 城市消歧、准确站点确认、统一坐标系与来源 | 11—14 |

## 27. 后期扩展路线

只有第一版通过且实际使用暴露明确需求，才从以下方向选择下一项；不预建这些架构。

| 方向 | 开始条件 | 可选内容 |
|---|---|---|
| 更稳定的途中使用 | 真实旅行表明离线资料和单实例不够 | PWA、可靠离线更新、明确支持的通知方式 |
| 更丰富的输入 | 高铁识别稳定且有实际机票需求 | 机票/酒店/预约凭证识别、更多文件格式 |
| 更长更复杂旅行 | 2～4 天产品已稳定 | 多城市、5 天以上、跨时区、多币种、海外地图 |
| 服务替换与覆盖 | 当前提供方确实受限 | 第二 AI/地图适配器、合法授权票务数据 |
| 更深入的偏好 | 用户反复修改同类安排 | 常用偏好、步行容忍度与可解释排序改进 |
| 数据跨设备 | 确实需要电脑手机各自编辑 | 登录与同步，届时再评估数据库和冲突解决 |
| 更细交通体验 | 当前路线资料满足不了需求 | 更准确未来时刻路线、航班状态、无障碍选项 |

微服务、复杂多 Agent 和企业权限不是必经升级路线。只有可测量的问题证明需要时才讨论，不能因为用户量可能增长就提前引入。

## 28. 给 Codex / DSH 等工具使用的开发规则

可直接复用的完整版位于同目录《AI Coding 执行总规则》。用户只需给后续 AI 一张对应的[阶段任务卡](阶段任务卡/README.md)，由 AI 自动读取规则、开发进度和前一阶段验收/交接，不要求用户每次复制两份总文档。

### 28.1 每次任务的执行顺序

先读用户本次要求、主文档当前阶段、项目实际文件和上一阶段证据 → 检查依赖和数据安全 → 只实现当前主要功能 → 自己启动 → 自己测试 → 自己修复 → 根据 DoD 验收 → 更新状态 → 在已授权范围内决定是否继续。

禁止因为“上一位 AI 说做完了”就跳过状态核对；也禁止因为看见完整蓝图就一次性实现全部阶段。

### 28.2 防失控规则

1. 不一次性写完整项目，不提前实现下一阶段，不为未来创建复杂架构。
2. 不擅自缩减本文件的第一版必需能力；实现遇到限制时说明具体条件和替代方案。
3. 不让模型代替程序做时间、费用和硬约束计算，不把推测写成事实。
4. 不要求作者读代码、改配置文件、运行命令、查看控制台或技术验收。
5. 用户已授权的日常开发、修复和必要验证由 AI 继续完成，不反复索取同一授权。
6. 账号、密钥、付费及公开部署缺少必要条件时，先完成可独立准备的部分，再说明最少所需内容；不得伪造通过。
7. 架构必须调整时说明当前具体问题、影响和回归范围，完成必要修正，不扩展为大重构。
8. 每阶段保留可运行状态；测试和迁移不破坏真实旅行。
9. 测试必须实际执行，证据不得编造；没有真实服务、浏览器或导出检查能力就写未验证。
10. 阶段通过后再进入下一阶段。若任务只授权一个阶段，完成后交接；明确授权连续推进时按顺序自动进行。
11. 只读问题定位、常规修复和验证属于正常技术工作；用户确认票面或是否应用新行程属于产品交互，两者不要混淆。
12. 不追求无关的百分之百完美；优先能用、简单、稳定、精致、扩展性。

### 28.3 项目内的最小交接资料

开始开发后，由 AI 按需要创建并维护开发进度、实际启动说明、数据位置、当前架构说明和每阶段验收记录。采用少量 Markdown 文件即可，不建立复杂项目管理系统。

每个阶段记录：目标、当前状态、改动摘要、真实执行的测试、证据路径、外部服务已验证能力、遗留项、下一步。统一使用 docs/开发进度.md、docs/阶段验收/阶段-NN.md、docs/阶段交接/阶段-NN.md（两位阶段号），按[新窗口交接约定](阶段任务卡/新窗口交接约定.md)维护。实际实现偏离蓝图时同步修正文档并解释原因，保持下一位 AI 能接手。
