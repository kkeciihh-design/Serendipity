# 新窗口交接约定

适用项目：AI 旅行规划助手（Serendipity）。\
项目默认位置：C:/Users/11295/Desktop/Serendipity。\
使用方式：用户每个阶段开一个新窗口，把对应任务卡交给开发 Agent。一个窗口完成一张卡后停止。

**这是开发规范，不是已执行记录。当前是否有代码、哪个阶段通过，以实际项目和开发进度为准。**

## 1. 新 Agent 怎样接手

1. 先读用户本次指定的任务卡，不自行选择下一张。
2. 读本文件、项目中的《AI Coding 执行总规则》和开发进度。
3. 阶段 01 起，读上一阶段的验收记录、交接记录及本卡指出的相关历史记录。
4. 检查真实文件、依赖锁文件、启动方式、数据目录和现有改动，运行必要的基线检查。
5. 总文档只查本卡列出的相关章节及发现矛盾时需要的部分，不必每次从头阅读，也不把未来章节当成本次任务。

只有阶段 00 在确认没有应用代码时可以初始化项目。后续阶段必须接着现有项目做，沿用已经验证的技术栈、包管理器、数据位置和测试工具；不得因为开了新窗口就重新建项目。

上一阶段写了“通过”仍要核对证据和实际成果。缺少记录时先调查项目、复现必要检查并补充真实记录，不直接重做，也不伪造历史结果。如果前置能力确实未完成，明确指出应回到哪张卡；不要补写“通过”然后抢跑。

## 2. 本次授权范围

任务卡的执行指令仅在用户把它交给开发 Agent 实施时生效。阅读、整理或审查任务卡本身不授权开发。

实施时只完成当前阶段及其必要修复。完成后不开始下一阶段、不创建新聊天，也不替用户把卡片发到其他窗口。下一张由用户在新窗口发起。

用户不需要读代码、运行命令、查看控制台、自己调用接口或判断测试结果。AI 负责实现、实际启动、测试、修复、复测和技术验收；用户确认自己的票据、偏好、账号及是否付费，属于正常产品选择。

在既有授权内的普通开发和修复不反复询问。确实缺少密钥、部署目标、付费决定或工具能力时，先完成当前阶段可独立推进的部分，再说明最少所需条件。密钥通过设置页面填写，不要求发到聊天里。

同一项目不要同时在多个窗口实施不同阶段。如果发现有其他窗口正在修改重叠文件，先保留其工作并说明冲突；不强行覆盖，不引入复杂锁服务。

## 3. 技术与业务约定

拟选技术栈为 Next.js、TypeScript、Tailwind、SQLite/Prisma；阶段 00 实际核验并记录兼容版本。之后以项目中已采用的实现为准，不为换 Agent 随意换栈。

按需引入功能：数据库从阶段 03、真实 AI 设置从 04、地图从 11、路线从 13、红线从 15、截图从 16、执行界面从 23、导出从 24 开始。未来规格不要求现在预建模块。

所有阶段继承以下约定，只对已经引入的模块实施：

- 时间保存完整日期和时区，金额用整数分，耗时用秒，距离用米。地点与到访事件使用不同的稳定 ID。
- 时间红线、金额汇总、顺序和硬约束由程序计算；模型负责理解、候选和解释。时刻相关路线按适用班次，从建议出发时刻正向复核，并另查当前时刻；缓存包含完整日期及适用时刻/窗口，最多复核 3 轮（含首次），缺能力或仍不一致则如实降级。
- 地图耗时若已包含候车、换乘、步行，不再重复累计；一个交通环节的时间和费用只计一次。
- 预算确定程度与支付状态分开；未知不等于零，取消项目不等于退款。模糊偏好不被偷偷变成严格上限。
- 来源核验到字段，保留获取时间、适用日期、过期和冲突状态。预测仍是预测，示例不变成真实事实。
- 票据先识别为草稿，确认关键字段后才生效。同班次同行票不自动合并；不为去重采集证件信息。14 引入稳定 ticketId 与 draft/active/cancelled/replaced，只有 active 参与交通硬约束；用户确认已退票/替换事实后停用指定旧票，保留其他有效票和已发生费用，16 复用同一入口。
- 同一旅行只有一个当前计划版本。05 引入 requestRevision：需求编辑递增并清除当前确认，旧提取不得覆盖新输入；06 的 PlanVersion 保存所用修订和不可变 requestSnapshot。旧计划的展示、普通编辑校验、预算和导出使用自身依据，新需求未应用时标待更新。新生成/重规划核对当前确认需求 R、计划 V 及已引入状态版本，不给旧输出补最新版本号。
- 重规划保护当前 active 票据、固定预约、用户锁定、已完成事项和已发生费用。需求变化不解除这些约束；真实票据/费用更新可沿用当前计划旧 R 并继续标待更新，不因新需求待确认而丢弃事实。红线是派生结果，要按新路线重算。22 真正应用时复核最新时钟，事务外重查路线，提交时再查版本和时间窗口；实质变化重新预览，不可行则拒绝应用。
- 导出读取计划及其 requestSnapshot、清单和执行状态的一致快照，不拼接当前待更新需求。隐藏住址时同时处理文字、坐标、地图路线、导航链接和内嵌数据。
- 服务端密钥不出现在页面、日志、导出和普通备份。按提供方设计公开的地图浏览器 Key 单独限制域名和额度。
- 测试数据与真实旅行分开。迁移前由 AI 备份；不得靠删除数据库解决问题。用户备份页面到阶段 28 才实现。
- 28 引入持久实例 dataGeneration 与恢复屏障，回补所有既有业务提交入口，之前不预建恢复模块。普通重启保留代际，旅行备份不带回代际；恢复成功或失败回退后均换代再开放写入，中断先安全处理恢复状态。旧请求/旧页面须重读业务状态，不得仅给旧载荷补新代际；28 后技术恢复也遵守此规则。
- 公共验收门槛按当前阶段已引入能力适用：08 不提前验09预算，11/12 不提前验13路线或14门到门，24/25/26 不提前验后续导出格式；本阶段必需的真实服务或验证条件缺失不能写成不适用。

日常配置放设置页。默认本机运行；远程部署只在用户明确选择并授权后实施。一次只使用一个主要数据实例，不假定本地和远程会同步。

## 4. 三份固定接班记录

项目内只用三类 Markdown 记录，不另建复杂管理系统。NN 是两位阶段号，例如 00、09、15、30。

| 文件 | 谁维护 | 记录什么 |
|---|---|---|
| docs/开发进度.md | 当前开发 Agent | 当前状态、已通过阶段、实际入口、栈/数据位置、待解决条件、下一张卡 |
| docs/阶段验收/阶段-NN.md | 执行本阶段的 Agent | 实际测试及结果、证据、代码版本/变更范围、明确结论 |
| docs/阶段交接/阶段-NN.md | 执行本阶段的 Agent | 下一窗口必须知道的实现事实、接口/数据约定、启动方法、已知限制 |

实际执行后再创建对应阶段记录。不要预先生成 31 份“通过”报告，也不要把任务卡当成验收证据。

开工时在进度中记录本阶段“进行中”；中断时说明停点；只有所有必过项通过才能将其标为“通过”。“下一张建议卡”不是连续推进授权。

## 7. 如何判断能否交下一张卡

结论统一为：**通过 / 不通过 / 外部条件待验收**。

实现错误或测试失败属于“不通过”，AI 继续修复。确实缺少真实服务、必要凭据或测试能力才属于“外部条件待验收”；不能把所有错误归给用户。

模拟通过、代码写完、构建成功，单独都不是阶段通过。正常流程、关键异常、数据、真实依赖和实际页面检查满足本卡 DoD 后，才可以交接下一张。

如果无法完成本阶段，保留已完成且可运行的成果，写清复工入口；下一窗口继续同一张卡，不跳过失败项。轻微非阻断问题可以登记，不无限打磨。
