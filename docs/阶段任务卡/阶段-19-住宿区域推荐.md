## 4. 本阶段详细规格

### 目标

帮助用户选择这趟旅行住哪里更合适。

### 用户能看到什么

2～3 个住宿区域的取舍、参考价格和交通关系，资料可得时附酒店候选。

### 功能要求

同时考虑当天活动、次日活动、返程站、预算和入住/寄存条件；区分区域参考点与已订酒店；酒店价格和房态分别表达。

### 页面

住宿推荐区、地图区域/参考点、酒店确认面板。

### 交互

比较区域 → 选择偏好 → 需要时确认实际酒店；确认后重新计算相关路线、费用和红线。

### 数据

区域候选、推荐理由、参考价、区域标识、实际酒店可选、入住日期/房数/晚数。

### 技术实现

复用地点、路线、预算和来源；区域未定不伪造精确酒店位置。

### 测试

早去返程站、主要活动较远、多人多房、未到入住时间、区域无酒店资料、确定酒店后路线重算。

### 验收标准

推荐理由说明位置取舍；至少一个区域符合当前约束或明确无解；不承诺有房和已预订。

### 常见失败情况

只推荐市中心、忽略第二天、把区域中点叫“你的酒店”、住宿夜数错误。

### Definition of Done

通用 DoD 通过，选区到确认酒店的实际流程与相关计算通过。

### 本阶段不做什么

不自动订房，不做全网房价比较、实时房态或酒店会员体系。

## 5. 按这个顺序完成

1. 比较2—3个合理区域，解释当天活动、次日和返程站之间的取舍。
2. 展示区域参考点、预算区间及已知入住/寄存条件，有资料时附少量酒店候选。
3. 允许用户确认实际酒店、房数、晚数与日期，区分参考区域和确切住宿。
4. 确认酒店后重算交通、费用和红线，检查提前入住和返程衔接。
5. 运行下面的验收项，发现失败自行修复并复测；保存实际结果，不复制预期冒充已通过。
6. 更新开发进度、本阶段验收和交接文件，向用户提供入口与结论，然后停止。
