## 4. 本阶段详细规格

### 目标

用连续时间轴组织每天行程，并支持基础编辑。

### 用户能看到什么

每天什么时候做什么、上一项如何接到下一项；可修改时间、时长、备注并锁定重要安排。

### 功能要求

按日期排序，区分活动和交通；支持跨日；允许编辑、移除非固定活动和锁定；修改后按所编辑计划自己的 requestSnapshot 执行当前可用的约束检查并保存，继承其 requestRevision。新需求未应用时仍标待更新，不把普通编辑改标成已采用最新需求。后续路线、费用和红线接入同一更新入口。

### 页面

旅行详情时间轴与简短编辑抽屉。

### 交互

切换天 → 点事件 → 修改/锁定 → 保存或取消；冲突展示原因，不自动挪动被锁定安排。

### 数据

事件 ID、日期、顺序、起止时刻、状态、锁定与备注，继承原需求修订/快照的计划新版本。

### 技术实现

统一日期计算和事件校验；交通展示行不重复占用时间或创建费用。

### 测试

跨午夜、活动重叠、负时长、锁定后删除、取消修改、改后重开；键盘和手机编辑流程；T29 的本阶段部分：最新需求待更新时编辑旧计划，校验依据和保存后的需求快照保持一致。

### 验收标准

时间顺序正确；编辑可保存、可取消；固定安排不被静默改动；缺路线时不假称已核实交通可达。

### 常见失败情况

只按时分排序、日期丢失、拖动导致 ID 变化、酒店整晚记录误占所有活动。

### Definition of Done

通用 DoD 通过，跨日与编辑冲突用例通过，完整日程能逐项读懂。

### 本阶段不做什么

不做复杂拖拽编排、地图联动或 AI 重规划。

## 5. 按这个顺序完成

1. 把每日事件按完整日期时间显示，明确活动和交通区别。
2. 提供简短编辑面板：时间、时长、备注、锁定与移除非固定活动。
3. 修改后按该计划的 requestSnapshot 检查当前已有约束并保存新版本，继承原 R；最新需求待确认或待应用不改变该依据。取消不修改，被锁定的安排不可静默移动。
4. 测试跨日、重复到访、重叠、负时长和刷新；为后续计算保留统一更新入口而不预建模块。
5. 运行下面的验收项，发现失败自行修复并复测；保存实际结果，不复制预期冒充已通过。
6. 更新开发进度、本阶段验收和交接文件，向用户提供入口与结论，然后停止。
