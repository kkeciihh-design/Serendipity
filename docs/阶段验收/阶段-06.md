## 功能核对

- 2 天真实生成：创建并确认两天长沙需求后调用生成接口；预期生成可保存的基础草稿；实际生成 PlanVersion V1，绑定 requestRevision 2，14 个事件，包含唯一去程、唯一返程、每日餐饮/活动/休息/准备事项、第 1 天住宿区域和待确认事项，结构校验无错误；证据：[阶段-06-real-service.json](证据/阶段-06-real-service.json)。
- 4 天真实生成：创建并确认四天成都需求后调用同一入口；实际生成 V1，28 个事件，覆盖 4 个日期，去返程、餐饮、活动、休息、准备事项、住宿区域和待确认事项齐全；证据：[阶段-06-real-service.json](证据/阶段-06-real-service.json)。
- 需求与计划双版本保护：V1 生成后修改目的地并确认新修订，旧 requestRevision 2 的生成请求返回 409；基于修订 3 生成 V2 成功；随后携带旧计划版本 V1 的请求返回 409。目的地、日期、人数变化的旧结果拒绝均由集成测试覆盖；证据：真实服务 JSON 与 `tests/plan-version.test.ts`。
- 固定需求快照：V1 保存的 `requestSnapshot.destination` 为长沙；新需求生成 V2 后，V1 历史行仍保留长沙快照，页面可通过 `?planVersion=1` 打开旧版本；证据：真实服务 JSON、`listPlanVersions` 检查与 `app/trips/[id]/page.tsx`。
- 估算与待确认：真实模型事件的 `costStatus` 均为 estimated 或 pending_confirmation，页面显示“估算/待确认”，不宣称余票、确切价格、营业状态、天气或路线已核验；证据：真实服务 JSON 与浏览器测试。
- 结构与异常校验：缺返程、缺每日准备事项、事件重叠、重复 ID、日期不匹配、负时长、格式错误、超低预算均被程序校验；低预算输出结构错误为 0 时保存为 needs_review 并显示警告，不会静默标成完全可执行；证据：`tests/plan.test.ts`。
- 取消、重复和失败保护：同一旅行只允许一个生成任务；取消在提交前检查 AbortSignal，不写计划；无效输出最多修复一次，仍失败不覆盖已有计划；重复提交被 409 拒绝；证据：`tests/plan-version.test.ts`、`tests/e2e/plan.spec.ts`。
- 需求变更后的旧计划：保存新需求修订时当前 PlanVersion 标记 `requirementUpToDate=false`，Trip 状态改为待更新；旧计划仍按自身 requestRevision/requestSnapshot 展示，不用最新 TripRequest 覆盖；证据：`tests/plan-version.test.ts`。
